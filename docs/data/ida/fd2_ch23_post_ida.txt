已證實：raw handler table 的 index 23／24 對應
-----------------------------------------------

- 資料映像的 handler table 位於線性位址 `0x51de9`；同一批 LE 輸入的檔案
  偏移是 `0x51be9`。little-endian raw entry 23 為 `0x14c1e`，依 object
  base `0x10000` 解析成線性位址 `0x24c1e`；entry 24 為 `0x14df2`，解析成
  `0x24df2`。這只固定 raw table consumer／函式邊界，不把 table index 直接
  命名成玩家戰次。
- `0x24c1e` 是 IDA 識別的 `sub_24C1E`，其 caller 是 `0x25e23` 的
  `call dword ptr [eax*4+0x51de9]`；`0x24df2` 是相鄰 raw entry 的獨立函式。
  map／LOADCH context 可作 internal chapter 23 候選，但玩家戰役 owner、
  一般玩家 provenance 與 campaign handoff 仍未閉合。

已證實：`0x24c1e` 的兩段計數流程
----------------------------------

- `0x24c4c` 呼叫 `0x15f84`，text index 2；`0x24cad` 再呼叫同一對白
  播放器，text index 3。兩者的文字來源是 `FDTXT_024`，但不代表
  玩家第 23 戰節點 `postbattle_ch23_persist`；依 FDTXT／map owner 與正式
  campaign 對齊，本 raw ch23 handler 對應的是玩家第 24 戰的
  `postbattle_ch24_persist`，目前尚未接線。
- 第一段每個內層迴圈開始前先在 `0x24c81` 呼叫 `0x24d22(EDI)`，
  `EDI` 依序為 2..9；接著在 `0x24c61` 呼叫 `0x11cac(1)`，再於
  `0x24c6b` 呼叫 `0x17aa9(1)`。`EBX` 每段從 0 累加至 29，共 30 次。
- 第二段每個 outer stage 迴圈開始前先在 `0x24cf2` 呼叫 `0x24d22(EDI)`，
  `EDI` 依序為 10..14；接著在 `0x24cc1..0x24ce7` 每個 stage 迴圈 12 次：先以 raw
  PUSH 順序 `[ESI,255,0]` 呼叫 `0x11d40`，再 `0x11cac(0)`、
  `0x17aa9(1)`；`ESI` 在 outer stage 之間沒有重設，整段五個 stage 共 60
  次，正式參數的 delta 依序是 `0..59`。
- `0x24cff` 透過 `0x375c0` 將 `0xa0000` 起點的 `0xfa00` bytes 清零，
  接著 `0x24d13` 呼叫 `0x11506`，`0x24d18` 遞增章節。這個尾端順序是
  已證實的 sync／chapter 行為，不等於已證實的戰間整備消費端。
- **2026-08-21 勘誤（已證實）**：先前把「handler 入口 latch 值」列為
  第一個呈現的阻擋並不成立。直接控制流程是 `0x24c81→0x24d22(2)` 後才到
  `0x24c61→0x11cac(1)`；第二段同樣是 `0x24cf2→0x24d22(10)` 後才到
  `0x24cc1→0x11d40` 與 `0x24cd3→0x11cac(0)`。因此固定檔案 seed `0x01`
  與進入 `sub_24C1E` 前的 latch 都不會決定兩段的第一個呈現；每段實際
  可消費的值已由同一函式先寫成 stage 2..14。仍需保留的時序條件只有
  `sub_11EEE` 依 BIOS tick 是否變化，決定該次 draw 是否執行
  `sub_24D22(0)`；不能把它改寫成「每個重製影格固定旋轉一次」。

已證實：`0x17aa9(1)` 是 BIOS tick 等待
----------------------------------------

- `0x17aa9` 讀取 `[0x46c]`，以 `dword_53A2C` 保存前次 tick；差值小於
  immediate `1` 時持續輪詢，並處理 `0x10000` wrap。其時間單位是 DOS
  BIOS tick（約 54.9 ms），不是固定 60 Hz frame。
- 重製編譯器已有 `0x17aa9` 正整數 immediate → editable `delay` 的通用
  lowering（每 tick 以 3 個重製 frame 表示）；這只固定等待原語，不代表
  ch23 的完整 renderer 時序已閉合。

已證實：`0x11d40(0,255,ESI)` 的每段 12 次／整段 60 次 DAC 更新
------------------------------------------------------------------

- `0x11d40(start,end,delta)` 逐一讀取 `dword_53A65 + 3*index` 的 RGB
  三元組，減去 `delta`、負值夾到 0，再寫入 VGA DAC ports `0x3c8/0x3c9`。
- ch23 的直接指令在 `0x24cc1` 先 push `ESI`、`0xff`、`0`；因此 formal
  參數是 `(0,255,ESI)`，而不是 raw PUSH 順序看似的 `(ESI,255,0)`。
  `ESI` 只在 `0x24cb5` 初始化一次，沒有在 `0x24cf2` 重設；因此五個
  outer stage 的 12 次內層呼叫合計為 `ESI=0..59`（已證實）。
- 每次 palette 更新後仍有 `0x11cac(0)`、`0x17aa9(1)`；下一個 stage
  開始前再呼叫 `0x24d22(EDI)`。重製端現以兩個嚴格驗證的
  `native_ch23_loop` 可編輯 beats 保留這 60 組 register-bound palette、
  重繪、tick 與 latch setter 的原始位址。執行器在沒有 indexed／latch
  adapter 時明確失敗即關閉，因此仍不建立 `postbattle_ch24_persist` binding。
- `0x4dfcc` 讀取線性位址 `0x60003` 的 31 組 RGB 三元組；其
  `byte_60002=0..15` 以 `3*phase` 為起點，將連續 16 組寫入 DAC
  `0xe0..0xef`。IDA 偽代碼的 `BYTE1(v2)=-32` 與 Docker Capstone 的
  `mov ah,0xe0`／`out dx,al` 共同固定這個高位索引；舊的低位索引
  說法已撤回。重製端 `ApplyNativeCh23PaletteCycle` 保留這個固定視窗
  與原始位址來源；它是 raw palette 原語，不代表完整 palette 時序已接通。
- **2026-08-21 timer owner 補證（已證實）**：合法 IDA Pro 9.4 偽代碼固定
  `sub_4DFC0()` 只回傳 signed BIOS low word `[0x46c]`。`sub_4DFCC()` 先以
  16-bit unsigned 差值比較 `(sub_4DFC0()-word_60000) >= 2`；未達兩 tick
  立即返回且不寫 DAC。通過才將 `byte_60002` 加一並以 16 wrap、寫
  DAC `0xe0..0xef`，最後把目前 tick 存回 `word_60000`。因此第二段雖每個
  draw 都呼叫 `0x4dfcc`，palette phase 並非每個 draw 必然遞增；重製規格
  必須保留獨立的兩 tick gate。程序進入 handler 前的 `word_60000` 與
  `byte_60002` 精確值仍屬動態 E2；E1 只可保存相對相位與已證實 gate。

已證實：保留原始名稱的 `0x24d22` raw staging 分支
--------------------------------------------------

- `0x24d22..0x24df2` 在 `arg != 0` 時只將低位元組寫入 `byte_51A10` 後返回；
  ch23 只傳入非零 stage 2..14，因此本 handler 不會走 `arg == 0` 分支。
- `arg == 0` 另配置 `latch*0x138` bytes，從
  `0x53aff + (0xc0-latch)*0x138` 複製，再由 `0xbf-latch` 向 0 倒序複製
  0x138-byte rows，最後釋放暫存區。這是獨立的 copy branch，不能泛稱
  淡入淡出或 indexed renderer。
- IDA 的直接資料交叉參照仍只在 `0x24d22` 內顯示寫入／讀取；但沿著
  `0x11cac→0x11eee` 的控制流程追查可見 `dword_53C03==23` 分支在 BIOS
  tick 改變時呼叫 `0x24d22(0)`。因此已證實存在間接消費端，`0x51a10`
  可附加註記為「312-byte staging 的列旋轉 raw latch 值」（已證實），
  但仍不可命名為 frame、palette 或一般畫面狀態。

已證實：`0x10652` 的 raw ch23 staging loader
-----------------------------------------------

- `0x10652..0x1088d` 先清理既有 `[0x53aff]`／`[0x53b03]`；在
  `0x107d4` 只對 raw chapter `[0x53c03]==0x17`（十進位 23）進入本分支，
  否則跳至 `0x1084a` 的其他章節處理。這是 chapter selector 與分支邊界的
  直接指令證據，不替 `0x53c03` 命名成劇情章節欄位以外的語意。
- `0x107dd→0x107ea` 呼叫 `0x36d16(0xea00)`，並把回傳指標寫入
  `[0x53aff]`。`0xea00` 恰等於 `0x138×0xc0`（312-byte row、192 rows），
  因而可證實這個 raw ch23 分支的 staging 配置大小與 owner pointer；仍不
  證明它就是重製端的 `nativeMapWork` 或最終 VGA 目的地。
- `0x107ef..0x10804` 以 raw stack 順序
  `push 0x2a; push [0x53b03]; push 0x1a4d; call 0x111ba`，再把回傳值寫回
  `[0x53b03]`。IDA 的同函式資料表證據已將此 raw 分支對到
  `FDOTHER.DAT` archive entry #42；本紀錄仍保留資源識別值 `0x1a4d`、
  索引／參數值 `0x2a` 與既有 handle 的原始位置，不替 #42 命名圖形用途。
- `0x10809..0x10820` 再以 raw stack 順序
  `push -1; push 0x138; push [0x53aff]; push 0; push 0; push eax;
  call 0x4e63d`，之後 `0x10823→0x10831` 呼叫 `0x37416` 釋放
  `[0x53b03]` 並清零該 global。這證實 loader 的 decode／handle cleanup
  邊界，但不替 `0x4e63d` 的參數命名成解壓縮、圖片或 palette 操作。
- `0x1083b→0x10842` 呼叫 `0x24d22(0)`；這是 loader 完成後的 zero-argument
  raw latch/copy 分支入口。此呼叫本身不能證明 handler 入口的執行期值；
  固定版檔案映像的 raw seed 已證實為 `0x01`，但入口 latch 的執行期值、
  中間 staging 偏移全域的生命週期及一般玩家 E2 仍未知；共用尾端固定目的地
  `0xA0504` 的位址／複製 ABI 另見下節。
- `0x1088d` 在 `0x108a6` 呼叫 `0x10652`，只證明此 loader 位於共用 chapter
  setup 的 caller 內；沒有證據把它接成 `postbattle_ch24_persist` 的正式
  renderer。重製端維持 fail-closed，不建立資源語意或畫面 adapter。
- 重製端 `fdother.DecodeNativeCh23Stage`／`BlitNativeCh23Stage` 只消費上述
  已證實的 #42、312×192、`0x4e63d` 透明 blit 邊界；它們保留 raw 幾何與
  RLE，不宣稱 #42 是背景、轉場或 UI。完整 indexed state／present adapter
 仍由 `native_ch23_loop` 的失敗即關閉閘門保護；該 runner 現要求呼叫端明示
 `0x24d22(stage)` 的原始 latch 回呼（raw-latch callback），不會在 handler stage setter 後
 自動執行 `arg==0` 列旋轉。列旋轉只可由具備 BIOS-tick／raw staging
 provenance 的共享消費端 adapter 提供。

已證實：`byte_51A10` 的固定版 raw data seed
---------------------------------------------

- 合法 IDA Pro 9.4 `ida_dump_bytes.py` 與 Capstone `data` 指令在同一固定版
  `FD2.EXE` 都讀到 `0x51a10:01 ff 05 00 ...`；因此檔案映像中
  `byte_51A10` 的 raw seed 是 `0x01`。這是輸入二進位的資料證據，不把相鄰
  `ff 05` bytes 命名成 latch 欄位。
- IDA 資料交叉參照只列出 `0x24d22..0x24df2`：非零參數在 `0x24d39` 寫入
  low byte，零參數在 `0x24d41/0x24d59/0x24d86/0x24dac/0x24dc9` 讀取它。
  因此「靜態 seed 完全未知」已撤回；但 `0x24c1e` 會在第一段與第二段
  迴圈間寫入 stage 2..14，固定檔案 seed 不能直接當成 handler 入口值。
- 固定 seed 仍不得強制注入重製執行期；但依 `sub_24C1E` 的直接控制流程，
  stage 2 已在第一個 `0x11cac(1)` 前寫入，所以入口 latch 不再是 production
  adapter 的阻擋。第一個 draw 是否執行 zero-argument `0x24d22(0)`，應由
  已證實的 `[0x46c] != [0x539f8]` 虛擬 BIOS tick gate 表示，而不是另猜
  一個固定初始結果。

已證實：`0x11cac→0x11eee` 透過 case 23 間接消費 raw latch
---------------------------------------------------------------

- IDA Pro 9.4 的 `0x11cac(a1)` 先更新 native tick/pose 狀態，只有
  `a1==0` 額外呼叫 `0x4dfcc`；兩個參數值之後都進同一條 indexed 路徑：
  `0x11eee(dword_53a49+32904,456,13,8,dword_53aa9,dword_53aad)`、
  `0x122dc`、`0x127a9`、`0x1acf3`，最後由 `0x11eb0` 把
  `312×192` bytes、stride `456` 的 staging copy 到 VGA。
- `0x11cac` 本身沒有直接讀取 `0x51a10`；然而它呼叫的 `0x11eee` 在
  `dword_53C03==23` 且 BIOS tick 改變時呼叫 `0x24d22(0)`，該分支以
  `0x138`（312）byte rows 對 `0x53aff` staging buffer 做列旋轉。因此
  `0x24d22` 的 setter／copy branch 是同一個 raw staging contract 的兩個
  入口，仍不可把它提升成泛用畫面幀或 palette index。
- Docker Capstone 逐指令核對 `0x11eee` 的 case 23 分支：`0x11eff` 讀
  signed BIOS tick `[0x46c]`，`0x11f07` 與 `[0x539f8]` 比較；`0x12096`
  只在 raw chapter `[0x53c03]==0x17`（十進位 23）進入此路徑，`0x120a7`
  再次檢查 tick，只有不相等時才由 `0x120af→0x24d22(0)`，接著
  `0x120b9` 把新 tick 寫回 `[0x539f8]`。因此「tick gate 完全未知」已
  撤回；已證實的 gate 是 BIOS tick 變化，不是固定影格延遲。
- 同一分支在 `0x120c6..0x120fe` 將 `0x53aff` staging、`0x138` raw
  row stride 與 `0xc0` rows 傳入 `0x11eb0`。配合 `0x10652` 的
  `0x107dd→0x107ea` 配置證據，現在已知 raw ch23 loader 是
  `[0x53aff]` 這個 staging owner pointer 的建立端；ch23 中間目的地公式與
  共用尾端固定目的地 `0xA0504` 已由 `0x11EB0` 參數閉合。2026-08-21 的
  producer／cleanup 勘誤另證實，`sub_24C1E` 的 quiescent handler loop 不在
  三個 transient offset producer 內，也不呼叫它們；因此此 handler 的
  中間目的地以三個 offset 全為零建立，不需由 PNG framebuffer 猜測替代。
- IDA Pro 9.4 的 `0x11cac` 函式本體也固定了 indexed 消費鏈：
  `0x11eee` 後依序呼叫 `0x122dc`、`0x127a9`、`0x1acf3`，再由
  `0x11eb0` 以 `312×192`、來源 stride `456` 複製到固定線性目的地；所有 caller 的
 直接交叉參照包含 ch23 的 `0x24c63` 與 `0x24cd3`。因此本檔不再把
  indexed frame／重繪消費鏈標記為未知；但這只證明靜態共用消費鏈，
  不代表重製執行器已具備其 raw state／latch adapter。
- 這也固定了兩段 ch23 loop 的差異：第一段使用 `0x11cac(1)`，第二段
  使用 `0x11cac(0)` 並額外觸發 `0x4dfcc`；兩者不可在可編輯腳本中折疊
  成同一個 generic redraw。重製端現已提供 `RotateNativeCh23Rows`、
  `ApplyNativeCh23PaletteCycle` 兩個 raw 原語，以及保留完整 call-site／
  stage 值的 `native_ch23_loop` 候選 beats；共用 indexed 消費鏈已由 IDA
  靜態閉合；固定版檔案映像的 raw seed 為 `0x01`。入口 latch 與三個
  transient offset 的舊阻擋已由本檔 2026-08-21 勘誤撤銷；尚未閉合的是
  依已證實 tick gate 驅動的重製 adapter、production binding 與一般玩家 E2。

已證實：ch23 staging／offset globals 的 owner 邊界
--------------------------------------------------

- IDA Pro 9.4 data-xref 與 Capstone 5.0.3 交叉核對 `0x53aed`、`0x53af1`、
  `0x53af5`、`0x53aff`、`0x51a10`、`0x539f8` 的直接讀寫：`0x53aff` 只有
  `0x10652..0x1088d` raw loader 配置、清理並交給 `0x11eee`／`0x24d22`
  消費；`0x51a10` 的讀寫只在 `0x24d22..0x24df2`；`0x539f8` 的比較／寫入
  只在 `0x11eee` tick gate。
- `0x53aed` 的寫入位於 `0x130a6=0x18`、`0x130e9=0`；`0x53af1` 的寫入
  位於 `0x132b3=0x18`、`0x132e6=0`。`0x53af5` 則由
  `0x12f84`、`0x130b0`、`0x13296`、`0x133ee` 累加，並在
  `0x12ff4`、`0x13153` 清零。這些寫入分散於 raw 函式
  `0x12eaa`、`0x1300d`、`0x13185`、`0x13315`，不是 `0x24c1e` 專屬
  producer。
- 上述位置只證明共用 indexed／角色呈現流程的 offset-state lifetime；
  不足以把欄位命名成 camera、viewport、framebuffer 或重製端
  `nativeMapWork`。

已證實：`0x11eb0` 的逐列複製 ABI 與 ch23 的實際目的地
---------------------------------------------------------

- 合法 IDA Pro 9.4 偽代碼與 Capstone 直接指令共同固定
  `sub_11EB0(a1,a2,a3,a4,a5,a6)`：逐列執行
  `memmove(a1,a3,a5)`，每列將目的端加 `a2`、來源端加 `a4`，共 `a6` 列。
  這裡只保留原始參數位置，不把 `a1..a6` 改名成高階 framebuffer 欄位。
- `sub_11CAC` 的固定尾端呼叫是
  `sub_11EB0(0xA0504,0x140,dword_53A49+0x8088,0x1C8,0x138,0xC0)`；
  因此共用 indexed 消費鏈的最後一段，已證實將 312×192 bytes、來源 stride
  `0x1C8` 的 work buffer 複製到固定線性目的地 `0xA0504`，目的 stride 為
  `0x140`。這是位址／複製 ABI 證據，不把 `0xA0504` 直接改名成現代
  framebuffer 物件。
- `sub_11EEE` 的 raw chapter 23 case 會先呼叫
  `sub_11EB0(dword_53AED+a1+dword_53AF5+0x1C8*dword_53AF1,

  producer／cleanup 證據，ch23 handler 的兩個 loop 使用零 offset，故來源
  staging 會複製到 caller 傳入的 `a1`；尚待實作的是保留 BIOS tick gate 的
  indexed adapter，而不是再猜三個 offset 的高階語意。
