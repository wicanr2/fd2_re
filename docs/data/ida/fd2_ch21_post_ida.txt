# FD2 raw ch21 post（玩家第22戰）IDA Pro 9.4 證據

## 輸入與工具

- 輸入：`FD2.EXE`
- 大小：357074 bytes
- MD5：`b97caf2239a27a896069d03549d96e1e`
- SHA-256：`222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f`
- 工具：使用者授權的 IDA Pro 9.4，於 `fd2-ida-authorized-local` Docker
  映像中，以 IDA flat linear address 執行；資料庫是由唯讀原版複本在
  `/tmp/fd2-ida-ch21*` 一次性重建，沒有修改原始檔或儲存庫內資料庫。
- 交叉驗證：IDA `tools/ida_probe_functions.py`、
  `tools/ida_dump_bytes.py`、`tools/ida_probe_data_xrefs.py`、
  `tools/ida_dump_pseudocode.py`；loader 另以
  `sub_1088D`／`sub_10B4E`／`sub_10C50` 的同一 IDA 資料庫重建。匯出只保留
  位址、指令、原始位元組與資料交叉參照。

## 已證實的直接指令

- handler 入口 `0x244b6`，IDA 函式範圍 `0x244b6..0x24618`；唯一主表
  呼叫者為 `0x25e23`（`funcs_25E23[eax*4]`）。
- `0x24512` 呼叫共用 `sub_233C6`（範圍 `0x233c6..0x234bb`）。呼叫前
  先複製三組 16-byte 表，再傳入 16 格迴圈、特殊位置與鏡頭參數。
- `0x24539`、`0x2456a`、`0x245a7` 分別呼叫 `sub_15F84`，原始文字索引
  為 4、5、6；每次前置 `dword_53A79`。
- `0x24543` 呼叫 `sub_1366A(0x41)`，`0x24580` 呼叫
  `sub_1366A(0x42)`；這裡只證實 raw acting immediate，不在本檔命名角色。
- `0x24576` 呼叫 `sub_135DD(0x10,0x10)`；`0x245b3` 呼叫
  `sub_135DD(0x0e,0x10)`。原始 PUSH 順序保留在 handler JSON。
- `0x245ce` 呼叫 `sub_24618`，原始 PUSH 順序為
  `8, 10, [0x53abd]+3, [0x53ab9]`；`0x245db` 延遲 500 ms。
- `0x245fa` 呼叫無參數 `sub_1F882`；後續 `0x245e3..0x245f7` 與
  `0x245ff..0x24610` 是兩次 `memset(0xA0000, ...)`，再跳到共享尾端
  `0x239ac`；`0x239b1` 設定下一章 22。

## 已證實：`0x233c6` layout ABI、special slot72 與演出 65／66

- IDA Pro 9.4 的 `0x244b6` 直接指令（PUSH 由右至左）為：
  `0x52273`、`0x52283`、`0x52293` 三組 16-byte 表，接著
  `start=0`、`end=0x0f`、`special_slot=0x48`、`special_x=0x16`、
  `special_y=0x19`、`special_pose=0x02`、`camera_raw_x=0x10`、
  `camera_raw_y=0x12`，最後呼叫 `0x233c6`。這些是原始參數與位址，
  不是角色名稱或部署規則。
- `sub_233c6` 對 slots 0..15 逐筆寫入 80-byte runtime records 的 X、Y、
  pose；當 special index 非零時另寫 slot 72 的 `(22,25,pose 2)`，並將
  raw camera globals 設為 `(16,18)`，接著重設游標、重繪並等待 200 ms。
  layout 表與 special slot 是**已證實**；把 raw camera `(16,18)` 轉為重製
  像素 `(384,432)` 依既有 24-pixel tile ABI，屬**強推論的重製映射**，
  不取代原始數值。
- `0x52273`／`0x52283`／`0x52293` 的完整原始位元組如下；重製候選檔保留
  同一順序與 slot identity：

  ```text
  X:    16 16 15 17 14 15 16 17 18 14 15 16 17 18 15 17
  Y:    16 14 16 16 17 17 17 17 17 18 18 18 18 18 19 19
  pose: 02 00 02 02 02 02 02 02 02 02 02 02 02 02 02 02
  ```

- 使用同一固定雜湊 `FD2.EXE`，以 Docker 內的
  `tools/export_acting_resources.py` 匯出後，resource `0x41`（十進位 65）
  有 2 個 frame、只寫 slot 1；resource `0x42`（十進位 66）有 50 個
  frame，涵蓋 slots 0..15 並直接使用 special slot 72。完整可編輯 frame
  表已保存於 [`ch21_post.json`](../../../remake/assets/cutscenes/acting/ch21_post.json)，
  這是**已證實的資源轉錄**，不是角色命名或一般玩家畫面證據。
- `remake/assets/cutscenes/bindings/ch21_post_candidate.json` 將上述 layout、
  acting、兩段 PAN 與 `0x24618` indexed transition 綁成可編譯候選；候選
  編譯回歸確認所有 slot／frame／游標來源均保留原始 provenance，但檔案不會
  自動接入 `postbattle_ch22_persist`。

## 已證實：`0x1f882` 是可重用的 64-step palette 淡出原語

- `0x1f882` 的共享尾段以 `EBX=0..63`（含兩端）逐步呼叫
  `0x11d40(0,255,EBX)`，每步等待 2 ms；它是 baseline-minus-delta 的
  原生調色盤淡出，不是同步／等待輔助器。此語意已由 Docker Capstone
  固定，並在 SDD 的 native palette IR 與 compiler regression 中保存。
- 因此 ch21 候選的 raw unknown 記錄只剩 `0x24618` indexed transition；
  `0x1f882` 雖可 lower 成 `native_palette_fade_out`，仍不能因此解除
  `postbattle_ch22_persist` binding，因 frontier 的一般玩家 runtime trace、
  postbattle record 內容與 indexed 畫面狀態仍未閉合。

## 已證實：`0x24618` 的九段 indexed transition 時序與固定 present

- 合法 IDA Pro 9.4 偽代碼與 Docker Capstone 在 `0x24618..0x24754` 對上：
  配置 `0x25680` bytes 的暫存區，先以 `0x11EEE` 建立初始 indexed work，
  再呼叫 `0x25A96(dword_53B13,11,1)`。迴圈由 raw `EBX=9` 倒數到 `1`，
  每段先複製完整 work buffer，再呼叫 `0x22046`，接著由
  `0x11EB0(0xA0504,0x140,dword_53A49+0x8088,0x1C8,0x138,0xC0)`
  複製 312×192 rows 到固定線性目的地 `0xA0504`，每段等待 5 ms。
- 迴圈結束後釋放 `0x25680` bytes 暫存區，等待 500 ms；再以
  `0x11DF2(0,255,delta)` 執行 `delta=0,2,...,62` 的 32 段調色盤更新，
  每段等待 4 ms，最後呼叫 `0x1D4CB`。這些是**已證實的時序／複製 ABI**，
  不是 generic fade 或同步替代品。
- `0x245ce` 的呼叫端仍保留原始 PUSH 順序
  `8,10,[0x53abd]+3,[0x53ab9]`；本節不把未由完整 caller／runtime state
  閉合的暫存器／堆疊欄位改名成游標、半徑或角色資料。重製端已有可編輯
  `indexed_transition` 時序與來源專屬游標橋接，但 frontier record、完整
  indexed state 與一般玩家 E2 尚未閉合，故不建立正式 campaign binding。

## 原始布局表（已證實）

IDA `ida_dump_bytes.py` 直接讀取下列線性位址：

```text
0x52273: 16 16 15 17 14 15 16 17 18 14 15 16 17 18 15 17
0x52283: 16 14 16 16 17 17 17 17 17 18 18 18 18 18 19 19
0x52293: 02 00 02 02 02 02 02 02 02 02 02 02 02 02 02 02
```

依 `sub_233C6` 的寫入端，這三列只能安全描述為 slots 0..15 的 raw
X/Y/pose 輸入。呼叫端另帶 raw special/focus scalar；其數值為
`0x48, 0x16, 0x19, 0x02, 0x10, 0x12`，但在沒有同一 battle runtime
槽位與消費端追蹤前，不把它們升格為角色、部署格或玩家可見鏡頭語意。

## map21 loader 指令與資源（loader 欄位已證實；frontier 為強推論）

- `sub_1088D` 範圍 `0x1088d..0x10b4e`：`0x108c9..0x1091d` 依
  `3*map+2`、`3*map+1`、`3*map` 讀取 FDFIELD positions/control/field；
  `0x10987..0x10995` 將 control header byte+1/+2 寫入
  `dword_53BE7`／`dword_53BE3`，`0x1099a` 將下一個 runtime index
  `dword_53BEB` 設為持久名冊數，後續 `0x10b3e` 呼叫 `sub_10B4E(0)`。
- `sub_10B4E` 範圍 `0x10b4e..0x10c50`：`0x10bcc..0x10be4` 逐筆以
  26-byte row stride 取 control row，`0x10be4` 讀 raw byte+0x15，符合
  請求 group 才在 `0x10bee` 呼叫 `sub_10C50(row, group)`。
- `sub_10C50` 範圍 `0x10c50..0x11019`：`0x10c69..0x10c81` 以
  `dword_53BEB*0x50` 取得目的 runtime record，`0x10d6c..0x10d79` 以
  row index 取 raw group data，`0x11003..0x1100b` 完成 native constructor
  後遞增 `dword_53BEB`。這證實追加順序與 runtime index 來源。
- 全域 runtime buffer 的交叉證據（同一固定版 IDA／資料流索引，詳見
  [`26-per-chapter-event-handlers.md`](../../knowledge-base/26-per-chapter-event-handlers.md)）顯示
  `[0x53a45]` 先配置 `0x1e00` bytes，也就是 96 個 `0x50`-byte 槽；
  `[0x53BEB]` 是目前已追加記錄的 count，而不是配置容量。故 66→72→73→79
  只能描述候選的「已 materialize 數量」，不能被寫成原版只有 66 槽或 slot72
  在短前沿一定不存在。短前沿的 slot72 record 內容與 renderer 消費仍未由本檔
  閉合，重製候選閘門因此採保守失敗即關閉，不把物理 buffer 容量誤當成語意證據。
- Docker 讀取的 map21 資源雜湊：`FDFIELD_063.bin` 9004 bytes，MD5
  `5b6823738ad3ad6226ed65481020818b`、SHA-256
  `9cc8e97a4e0e963d48529cb85bb8a43ab305914eba0110a1d970cc773f22ae82`；
  `FDFIELD_064.bin` 1951 bytes，MD5 `653e458025a7994d87a60c22ca5c7191`、
  SHA-256 `2338bf283917ae5f7e3155c1d57a6895d41862438b64ce46b720662708ab9241`；
  `FDFIELD_065.bin` 518 bytes，MD5 `f350c11805833ecb38d3ba9b4e59f9c4`、
  SHA-256 `34a931a2870f6252593c41705509067718c773673882468e896922f4401ea57a`。
  控制 header 為 `15 10 46`，positions u16 header 為 86。
- 本輪對照檔亦固定為 `map21_units.json` 59147 bytes、MD5
  `cc15d98026d88d5b25fc8fc2bea65a22`、SHA-256
  `5f663fcfcc51a8f6fcce7fed879ca6920a51bbc9d9befc502a97684cc2dfd722`，以及
  `ch22.json` 16861 bytes、MD5 `c422ee15e07deb344c900e86800d9606`、
  SHA-256 `acf986deb0863bc167058c46ed7fdaf9a69472a65ed48e0cfc824d090cca03d6`。
- 因此 raw group0=50、group1=6、group2=1、group3=6、group255=7，配合
  `ch22.json` 回合3／5／7 的追加，候選 materialized frontier 為
  **66→72→73→79**。這是**強推論**，不是一般玩家 runtime trace；
  positions 的 86 是 70 筆控制列位置加16部署格，不能解讀成86個 runtime unit。

## `0x24618` 動態游標來源（原始來源與重製橋接已分別固定）

- `sub_10010` 的 IDA 直接資料流將存檔 buffer `+12490/+12491` 寫入
  `dword_53AB9`／`dword_53ABD`；`sub_11BFA`、`sub_11B48`、`sub_11B9B`、
  `sub_11C59` 的方向輸入路徑也直接遞增／遞減這兩個 raw globals，並同步
  更新 `dword_53AB1`／`dword_53AB5`。依左右邊界分支，`53AB1/53AB5` 是
  絕對游標，`53AB9/53ABD` 是畫面內的相對游標；這是保留原始位址的強推論，
  不以自訂名稱取代 raw 欄位。
- 第22戰 `0x245ce` 將 `[0x53ab9]` 與 `[0x53abd]+3` 作為
  `sub_24618` 的前兩個 raw arguments，後兩個為 `10`、`8`；因此
  `0x24618` 的 radial center 是**畫面內相對游標**加上原始 Y 偏移，不能
  用 PAN 結束位置 `(16,14)` 或任意固定 `tile_x/tile_y` 代替。
- 重製端 `HandlerIndexedTransition` 現已附加
  `cursor_source=native_relative_cursor` 與固定 `cursor_y_offset=3`，並以
  fail-closed resolver 將 `NativeMapViewState.VisibleCursorX/Y` 橋接到
  `tile_x/tile_y`；測試保留 raw provenance。這只閉合可重用的輸入橋接，尚未
  轉成 `postbattle_ch22_persist` 的 production binding，仍失敗即關閉；
  indexed frame input 與一般玩家狀態回歸仍待補足；候選編譯只證明資料與
  fail-closed adapter 可消費，不代表 renderer parity。

## 現況判定

> **2026-08-27 勘誤：** 本節下方「沒有正式 binding」只描述2026-08-09狀態，
> 已由73／79-slot正式 binding、節點視圖交接、三caller／11句原生對話及
> `preparation_ch23`存讀檔回歸取代。原始位址、指令與推論等級不變；目前證據見
> [`fd2_ch21_post_native_dialogue.md`](fd2_ch21_post_native_dialogue.md)。

- 推論等級：上述位址、指令、表位元組與文字索引為**已證實**。
- `remake/assets/cutscenes/handlers/ch21_post.json` 保留上述 raw beats；目前
  沒有正式 binding，故 `postbattle_ch22_persist` 仍**失敗即關閉**。
- map21 authored JSON 的 70 筆資料現在已與原生 loader 的 16／70 header、
  group 分布及事件追加順序對齊，故 **66／72／73／79** 是可追溯的候選
  materialized frontiers（強推論），不再把槽位數寫成完全未知。`0x233c6`
  的 layout ABI、special slot72 與 acting 65/66 的資源轉錄已由上述
  IDA／Docker 證據閉合為 E1 候選；仍需要原版一般玩家戰後 runtime trace
  證實各 frontier 的 record 內容與實際 renderer 狀態，才可建立 production
  binding。raw cursor／Y+3 的可重用橋接與候選編譯回歸已固定，但不提升為 E2。
- 本檔不是 renderer parity 或一般玩家 E2 證據；任何只依三組表、map 項目數
  或舊 generated binding 建立的 `town_ch23` 接線都應視為未證實。

## 2026-08-09 IDA 直接交叉參照複核（非破壞性）

同一份固定雜湊 `FD2.EXE` 以合法 IDA Pro 9.4 Docker headless 重新建立資料庫，
只讀取函式邊界、直接程式碼交叉參照（code xref）與原始指令；沒有改寫原始名稱、位址或運算元。
`sub_24618` 的直接呼叫者（caller）為：

```text
0x245ce  caller 0x244b6..0x24618
0x252ee  caller 0x250cc..0x25464
0x25848  caller 0x25757..0x25977
0x336e5  caller 0x336a0..0x338c4
0x33bb9  caller 0x33af1..0x33c9d
0x33c09  caller 0x33af1..0x33c9d
0x33c66  caller 0x33af1..0x33c9d
0x33ce2  caller 0x33c9d..0x33dba
```

同次複核確認 `sub_22046` 的直接呼叫者為 `0x21f4c`、`0x21fe0`、
`0x22388`、`0x225f6`、`0x226a1` 與 `0x246c7`。因此 `0x24618`／
`0x22046` 是共享的 indexed 轉場／重映射消費端，不能按單一戰後 handler
命名成角色演出或通用淡出。這項交叉參照只提升共享 caller 邊界為**已證實**；
它不提供各 caller 的戰役 owner、一般玩家 E2 畫面或 runtime frontier，
所以 `postbattle_ch22_persist` 及其他未具完整狀態的節點仍維持失敗即關閉。
