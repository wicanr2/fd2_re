已證實：`0x24754` 的戰後控制流程
----------------------------------

- `0x247b4` 先以 `0x233c6` 建立 16×17 的配置／場景資料，之後以
  `0x24b14(100)` 掃描 16 個原生單位索引。成功與失敗分支都保留原始
  對白與 acting 位址：`0x15f84` 的 text index 8／9、`0x1366a(71)`。
- 直接指令在 `0x247c6` 比較 `0x24b14` 回傳值與 `-1`，`je 0x247fb`；
  因此回傳不是 `-1` 才播放 text index 8／JOIN22，回傳 `-1` 才播放
  text index 9／`0x1366a(71)`。這個方向由原始跳轉固定，不由角色名稱推測。
- 接著以 `0x24bde(18)` 檢查 persistent record；成立時播放 text index 10、
  `0x1366a(72)`、`0x32975(17)` 與 text index 11。不成立時再以
  `dword_53BEF < 15` 分支到 text index 13／`0x112a5(19)`，否則播放
  text index 12、`0x1366a(72)`、`0x32975(17)`。這些是控制流程與 raw
  呼叫的已證實描述，不替 record 或角色建立未證實名稱。
- 共同尾端為 `0x11506`、章節遞增、text index 14、400 ms 等待，接著依序
  呼叫 `0x2189a(10,15,1)`、`0x24b4d(30)`、text index 15、400 ms、
  再呼叫 `0x2189a(10,15,1)`、`0x24b4d(30)`、text index 16、400 ms，
  最後呼叫 `0x2189a(16,30,1)`。
- 【2026-08-21 後續接線勘誤】以上一度只證明原版 handler 的靜態順序；
  現已由本檔後續 layout、constructor、consumer 證據建立正式
  `postbattle_ch23_persist` binding，並依既有 authored campaign 進
  `preparation_ch24`。這不把該節點宣稱為原版 E2 證據。

2026-08-21 `0x247B4` layout 與 LOADCH slot 順序勘誤（IDA 已證實）：

- 上面的「16×17」不是可直接實作的 layout 形狀。合法 IDA Pro 9.4 對
  `sub_24754`／`sub_233C6` 的 caller ABI 證實：`0x247B4` 傳入三張各17 bytes
  的 table、inclusive slot range `0..16`、special slot `17`、special
  `(x,y,pose)=(21,21,2)`，以及 camera `(14,14)`。三張 raw table 位於
  IDA Linear Executable 線性位址 `0x522A3`／`0x522B4`／`0x522C5`：

  ```text
  X[0..16]    = 14 14 12 13 14 15 16 12 16 12 13 15 16 13 14 15 13
  Y[0..16]    = 13 11 12 12 12 12 12 11 11 10 10 10 10 0f 0f 0f 15
  pose[0..16] = 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
  ```

  因此 materialized layout 是 slots0..17 共18筆；slot17 最後由 special
  實參覆寫，而不是第18張 table entry。這些位址、bytes、range、special 與
  camera 是「已證實」，角色名稱及故事語意仍不附加。
- `0x205DA→0x1088D` 的原始 LOADCH 建構順序也由同次 IDA 閉合。
  `0x1088D` 先令 `dword_53BEB = control[1]`，從 persistent array
  `[0x53BF7]` 依序複製最多 `control[1]` 筆80-byte records 到 runtime
  `[0x53A45]`；其後才呼叫 `0x10B4E(0)`，而 `0x10C50` 以
  `80*dword_53BEB+[0x53A45]` 追加 FDFIELD group0 並遞增 count。
  map22 固定版 FDFIELD control #67 的 raw header 是16個部署／persistent
  slots、70筆 map records；group counts 為
  `0:2, 1:24, 2:6, 3:6, 4:6, 5:6, 6:6, 7:6, 8:4, 9:4`，position #68
  的86筆則是前70筆 map positions＋後16筆部署格。故完整 materialized
  frontier 是 `16+70=86`，不是「70個 runtime slots」；開局原始順序至少是
  persistent slots0..15、group0 slots16..17，後續 groups append。
- 這直接推翻目前 legacy `ch23.json` 的「先70筆 FDFIELD、後 spawn_party」
  runtime 順序；ACT71／72 所用 slot16／17 在原版是 group0 兩筆，而非 raw
  roster 的第17／18筆。何時追加 groups2..9 仍受 event52 與四列 turn control
  約束；本證據只授權修正 constructor order，不把尚未閉合的增援時序冒稱 exact。

## 2026-08-21 `0x2189A` 完整實參與每輪資料流勘誤（已證實）

合法 IDA Pro 9.4.0.260610／Hex-Rays 在一次性、無網路 Docker 中重新建立
固定雜湊資料庫；資料庫只在 tmpfs，原版 `FD2.EXE` 唯讀。IDA 函式邊界仍是
`sub_2189A=0x2189A..0x219AD`、`sub_219AD=0x219AD..0x21A9E`；直接 caller
包含 `0x24978`、`0x249C4`、`0x24A10`。Capstone 5.0.3 對同一線性位址與
raw operands 逐項一致。以下結論不使用 Hex-Rays 錯置的 `retaddr` 變數名：

1. `0x218AB` 讀第二個實參，`0x218AF` 讀第一個實參。第一個實參先乘
   `0x50` 定位 runtime record；record `+0/+1` 各減 camera
   `[0x53AA9]/[0x53AAD]`，再形成
   `centerX=(x-cameraX)*24+12`、`centerY=(y-cameraY)*24+18`。
2. 第二個實參是初始 radius；`0x2198E` 每輪只以第三個實參累加 radius。
   因此三個 ch22 caller 的 raw `[10,15,1]`／`[16,30,1]` 是
   `(unitIndex, initialRadius, radiusStep)`，不是九參數 API。
3. `0x218EA` 配置精確 `0x25680` bytes；`0x21914` 只把13×8 terrain staging
   建到 snapshot `+0x8088`。每個 `i=0..9` pass 都先以 `memmove` 完整恢復
   snapshot 到 live work `[0x53A49]`。
4. `0x21922..0x2192C` 從 boot loader 的 FDOTHER #3 base `[0x53A6D]`
   取 offset-table entry `i`，故十輪依序消費 LUT `0..9`。`0x21942..0x21955`
   的七個實參由原始 push 固定為
   `sub_219AD(centerX,centerY,radius,12,0,192,lut)`；`0x219AD` 逐 scanline
   以 toward-zero `sqrt(radius²-dy²)*12/10` 計算 span，水平裁切在312 pixels，
   並由 `sub_4DB9C` 原地套用該256-byte LUT。
5. 每輪 remap 後才呼叫 `0x127A9` 重畫 unit／foreground objects，接著
   `0x11EB0(dst=0xA0504,dstStride=320,src=work+0x8088,srcStride=456,
   width=312,height=192)` 發布 viewport。十輪後才 free snapshot 並呼叫
   `0x11CAC(0)` 還原 steady frame。

這關閉了舊「`0x2189A` indexed 資料來源、`0x219AD` consumer 與每輪 radius
生命週期尚未知」的阻擋。高階畫面名稱仍未知；正式 adapter 只能依上述 raw
順序組合既有 terrain snapshot、`ApplyRadialLUTRemap`、
`RedrawNativeUnitPresentObjects` 與 viewport copy，不得改成泛用淡入淡出。

## 2026-08-09 `0x4dbfc` 原始遮罩原語複核（非破壞性）

> 【歷史勘誤】本節稍後所稱「重製端目前只保存 `byte+3` 投影」已被
> 2026-08-21 的 `State.NativeMapEventGrid` 實檔稽核推翻；舊句只保留用來追溯
> 錯誤形成原因，不再是現況斷言。

合法 IDA Pro 9.4 Docker 重新建立同一固定雜湊資料庫後，固定函式範圍
`0x4dbfc..0x4dc34`。它先從輸入指標讀取兩個 raw bytes，計算
`count = u8[base+0] * u8[base+2]`，再從 `base+4` 起逐筆以 4 bytes 步進；每筆
直接執行：

```text
cell[+3] = 0xff
cell[+2] = cell[+2] & 0x1f
cell[+1] = cell[+1] & 0x03
```

`0x24a92` 的 caller 只提供原始 `dword ptr [0x3a51]` 指標；IDA 同次列出
該函式共有 34 個直接呼叫點，故不能把它命名成 ch22 專屬清理器或只看成
單一畫面效果。這是**已證實**的 raw mutation contract，但重製的戰役狀態
目前只保存 `byte+3` 的投影，未保存同一 cell 的完整 `+1/+2/+3` 原始陣列；
因此 `ch22_post.json` 的 `0x4dbfc` 仍保留 raw unknown，不能猜測性降級成
單純 `reset_native_target_field`。2026-08-21 重核重製端現況後，這項「只保存
byte+3 投影」已是過時斷言：`State.NativeMapEventGrid` 由相同 FDFIELD export
保存四位元組 header 與每格完整 `+0/+1/+2/+3`，`resetNativeMapEventGrid`
也逐格執行 `+1&=3`、`+2&=0x1f`、`+3=0xff`。因此 raw state 已
`DATA-READY`；仍需在 SDD 明定 handler 的原子 mutation／rollback，不能僅因
helper 已存在就直接解除 campaign gate。

證據等級與限制
--------------

- 上述函式邊界、直接呼叫、迴圈次數、引數順序與幾何常數是 E1 靜態「已證實」；
  IDA 與 Capstone 都以同一份固定雜湊的 FD2.EXE、線性位址基準產出。

  命名；但 `0x2189A` 的 typed 三實參、十輪 LUT／radius／snapshot／object／
  viewport 順序與 `0x4DBFC` 完整 raw grid 已閉合。不得以這份靜態證據升格為 E2。
- 尚無未修改一般玩家 DOSBox 的第23戰戰後→城鎮／商店／整備／存檔擷取，
  也尚未證明 `town_ch23` 的實際節點。原有戰間邊界保持 fail-closed，待
  raw indexed adapter 依 SDD 通過 E1 後才可建立正式 binding；一般玩家路徑
  仍另列 PLAYER-E2，不反向抹除已證實的靜態資料流。
