# FD2 玩家第29戰候選 raw handler `0x2548c` 證據

## 輸入與 raw table

- 輸入：`FD2.EXE`，357074 bytes。
- MD5：`b97caf2239a27a896069d03549d96e1e`。
- SHA-256：`222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f`。
- 工具：合法 IDA Pro 9.4 Docker；Capstone 5 Docker（`tools/disasm_le.py`）。
- handler table 資料映像線性位址 `0x51de9`、檔案偏移 `0x51be9`。
- index28 的 bytes 為檔案 `0x51c59: 8c 54 01 00`，raw little-endian
  `0x1548c`，object base `0x10000` 後為線性位址 `0x2548c`。
- 相鄰 index29 為 `0x25757`；它是另一個終局 self-loop 候選，不可和 index28
  的玩家第29戰候選混稱。

## 已證實：函式邊界與逐段順序

IDA 將 `0x2548c..0x25757` 識別為 `sub_2548C`，唯一直接 caller 是
`0x25e23` 的 table consumer（`call funcs_25E23[eax*4]`）。Capstone 對
同一線性範圍逐項一致。以下保留 raw immediate、運算元與來源位址：

1. `0x254b6` 呼叫 `0x15f84`，文字 immediate `10`；`0x254c0` 呼叫
   `0x35bba(20)`。接著以 `[0x53a45]+0x640` 的 record 寫入 byte `+7=0x7e`、
   `+8=0x7e`；這是 raw mutation，不命名角色或狀態。
2. `0x254fb` 呼叫文字 immediate `11`；`0x25505` 呼叫 raw
   `0x10b4e(9)`；`0x25511` 的 push 順序為 `8`、`9` 後呼叫 `0x135dd`，
   保存為 raw PAN `(9,8)`，不覆蓋原始順序。
3. `0x2551d` 呼叫 `0x12cea(10,15)`；`0x25535` 呼叫 `0x22253`，五個
   raw push 依序為 `10,15,10,15,[0x53beb]-1`。該函式的 geometry／unit
   語意尚未證實，僅保存 raw call site。
4. `0x2555c` 呼叫文字 immediate `12`；接著 `0x24b4d(20)` 三次，兩個
   間隔各 raw delay `0x258`（600 ms）。`0x255c5` 呼叫文字 immediate `13`。
5. 再執行 `0x24b4d(20)` 三次，間隔為 `0xc8`、`0xc8`、`0x64`（200、200、
   100 ms）；最後一次為 `0x24b4d(40)` 後 delay `0xc8`。
6. `0x25682`、`0x25694`、`0x256a6` 各呼叫一次 `0x35e5a`，每次後 raw
   delay `0x12c`（300 ms）；`0x256d7` 再呼叫文字 immediate `15`。
7. `0x256eb..0x25701` 呼叫 `0x11df2(EBX,0xff,0)`，`EBX=0..0x3f`，
   每次 raw delay `4`；清除 64000 bytes 後 delay `0x320`（800 ms）。
   `0x25733..0x25748` 再呼叫 `0x11df2(EBX,0xff,0)`，`EBX=0x3e..0`，
   每次 raw delay `4`。
8. `0x2574a` 呼叫 `0x11506`，`0x2574f` 對 global `[0x53c03]` 做一次
   `inc`，`0x25756` 返回。函式本身沒有直接呼叫 town、shop、preparation、
   save 或下一戰節點。

## 文字與 owner 判定

固定版 `FDTXT_029` 的 count-aligned index map 將 raw string 10 對到
`ch29.json` scene2 line7；string 11 對到 scene2 lines8–10 加 scene3 line0；
string 12 對到 scene3 lines1–12；string 13 對到 scene4 line0；string 14
對到 scene4 lines1–10；string 15 對到 scene4 line11。跨 scene 的資料仍保留
`dialogue-index/count-aligned.json` 的逐字 mapping，不把它壓成單一場景。

現行 campaign 的 `battle_ch29` 使用 map28，且重製 handler 草稿
[`ch28_post.json`](../../../remake/assets/cutscenes/handlers/ch28_post.json)
已保存上述 raw call sites。map28、文字 index10..15、raw index28 與尾端
`inc [0x53c03]` 共同支持「玩家第29戰 post handler 候選」的 E1 判定；這不是
只靠 table index 的命名。

## 失敗即關閉邊界

- `0x35bba`、`0x12cea`、`0x22253`、`0x24b4d`、`0x35e5a` 的完整 indexed
  renderer／工作區擁有者仍未全部閉合；不得用 generic pan、acting、fade 或
  文字播放器取代它們。
- 未修改一般玩家戰後→整備／城鎮／商店／存檔的 E2 前，不建立
  `postbattle_ch29_persist→preparation_ch30` 正式 binding。既有
  `postbattle_ch29_persist` 仍保持 fail-closed；index29 `0x25757` 的終局
  self-loop 仍是另一條獨立 raw 路徑。
- 完整原始函式、雜湊與 call order 保存於本檔；後續任何 owner 修訂都必須
  追加勘誤，不得以 table index 覆蓋線性位址與 raw provenance。

## `0x25535 → 0x22253` caller payload 勘誤（2026-08-21）

本節只重審既有受版控證據是否充分，不重開已閉合的 `0x22253` callee。當前
工作環境找不到固定雜湊的 `FD2.EXE` 或既有 `.i64`，因此本節**沒有宣稱重新
執行 IDA**；工具與輸入仍引用本檔開頭已保存的合法 IDA Pro 9.4／Capstone 5、
357074-byte 固定版雜湊。沒有出現輸入雜湊差異、直接指令反證、同狀態執行
矛盾，或主證據缺少其聲稱的 writer／consumer，故不符合重開條件。

既有五個 direct caller 與 `0x22253` 函式體已證實其 C ABI 為：

```text
0x22253(unit, newX, newY, visualX, visualY)
```

`0x25535` 前的原始壓棧順序是
`10, 15, 10, 15, [0x53BEB]-1`。32-bit cdecl 由右至左壓入參數，因此這個
call site 的具型別 payload 為：

```text
unit    = [0x53BEB] - 1
newX    = 15
newY    = 10
visualX = 15
visualY = 10
```

這項結論等級為**已證實**：caller 保留原始位址／壓棧順序，callee 主證據
保留五參數消費端、`record+0/+1` 寫入時點，以及 11＋6＋10 full-present 與
18／24-row direct-VGA bridge。它只授權 compiler 針對來源 `0x25535` 將
`[0x53BEB]-1` 降成「執行當下最後一個 materialized runtime slot」，並以
`(15,10)` 同時作 new／visual pair；不得泛化成任意動態角色選擇器。

因此先前「`0x22253` caller payload 尚未證實」已失效。仍未關閉的是：

- Ebiten 對完整 indexed schedule 的原子 presenter 與失敗回復；
- `0x35E5A` 的 indexed DAC pulse presenter；
- 玩家第29戰在 post handler 入口的 materialized slot topology，以及
  group9 append 後 `[0x53BEB]-1` 的原版槽位對應；
- 正式 `postbattle_ch29_persist` binding、整備／存讀檔 E1 與未修改原版 E2。

在上述拓撲證據閉合前，caller payload 可以列為 `RE-CLOSED`／`DATA-READY`，
但 campaign 仍必須失敗即關閉。

## `0x254C0..0x254D8` 戰後前置 writer 與 `0x1DB65` consumer 補證（2026-08-21）

本節以同一固定雜湊 `FD2.EXE`、合法 IDA Pro 9.4 一次性 Docker 資料庫重讀；
位址仍為 IDA 線性位址。原始檔唯讀，資料庫只存在容器 tmpfs。以下保留原始
函式名與運算元；欄位只以 raw offset 命名。

- `sub_35BBA` 邊界為 `0x35BBA..0x35BF2`。參數20從 `0x254BE` 壓入；loop
  `0x35BCB..0x35BE9` 對目前 runtime count 內 slots `20..count-1` 逐筆把
  word `record+0x40` 清為0，然後在 `0x35BEB` 無參數呼叫 `sub_1DB65`。
- caller 隨後在 `0x254C8` 讀 `[0x53A45]`、`0x254CE` 加 `0x640`
  （`20*0x50`），並於 `0x254D4`／`0x254D8` 把 slot20 raw `+7`／`+8`
  各寫為 `0x7E`。既有 handler JSON 漏掉這兩筆直接 writer；正式 typed data
  不得只 lower `0x35BBA` 而省略它們。
- `sub_1DB65` 邊界為 `0x1DB65..0x1DEBE`。它掃描所有 runtime records 的
  raw `+0/+1/+5 bit0/+0x40`；若沒有符合可見視窗且 `bit0=0`、`word40=0`
  的 record，會把所有 `word40=0` records 的 raw `+5` 設成1後返回。若有，
  則先執行13次呈現迴圈（含 `0x11EEE`、`0x127E0`、每次一個 BIOS tick），
  再把同一集合 `+5=1`，接著以暫存畫面、`0x25A96([0x53EEC],3,1)`、
  `[0x53A81]` entries `0x44..0x4F`、`0x4E85B` 執行兩段各6次的
  疊圖／present，最後 `0x11CAC(0)` redraw。既有啟動載入與音訊消費端證據
  已分別確認 `[0x53A81]` 是 `FDOTHER.DAT #5` 的 LMI1 bank，`[0x53EEC]`
  是 `FDOTHER.DAT #31` 的 UI SFX pool，而 `0x25A96` 是 AIL sample wrapper；
  因此 archive、entry index 與 raw sample tuple 為**已證實**。entries
  `0x44..0x4F` 的高階圖像名稱、sample index 3 的玩家語意名稱，以及同狀態
  像素／聽覺輸出仍是**未知**，不得只用 generic redraw 或推測名稱冒充完整
  `0x1DB65`。

### 可編輯資料與執行期規格

1. 戰後 raw 前置資料必須原子保存：start slot20、清除 `+0x40/+0x41`、
   slot20 `+7/+8=0x7E`，以及後續 `0x1DB65` presentation gate。一般戰役
   constructor 只要對所有 consumer 欄位具備原生 provenance，即可用 typed
   `+0/+1/+3/+5/+0x40` 與 slot20 `+7/+8` transaction；`CONTINUE` 若另帶完整
   `0x50` projection，則每個 consumed field 必須先與 typed view 一致。
   缺欄位、partial raw projection或任一 view 不一致時零修改。
2. 已證實的正常 materialization 前沿為76；event74每次依序追加2筆
   groups4／5／6／7，event76 final再追加3筆group1。因此在沒有一般玩家
   E2進一步收窄前，可接受的 pre-post 前沿集合只能是
   `76,78,80,82,84,87`；group9再追加1筆，且 `0x25535` 動態選新尾端。
   這是由已證實 producer 推得的**強推論安全集合**，不是固定 slot93。
3. 本節先授權 raw writer 與 frontier validator 的 `DATA-READY`／窄
   `RUNTIME-E1`；`0x1DB65` 原資源 presenter、完整 handler binding、
   `preparation_ch30` 存讀檔及一般玩家 E2 未完成前，campaign 仍失敗即關閉。
4. presenter 的可編輯契約必須保留 `FDOTHER resource=5`、entries
   `0x44..0x4F`、`SFX pool=FDOTHER #31`、sample index `3`、第三參數 `1`，
   以及13＋6＋6個呈現邊界；這些 raw 識別值不得被未證實的語意名稱取代。

### `0x25511→0x2551D` 視圖連續邊界（已證實，2026-08-21）

`0x25511` 先呼叫 `0x135DD(9,8)`，它寫 camera 與 absolute cursor，
但不寫 visible cursor；緊接的 `0x2551D` 直接呼叫
`0x12CEA(15,10)`，依當下 visible cursor 與 13×8 安全帶逐格更新
camera、absolute 與 visible 三對全域。所以戰後 handler 不可把
`0x135DD` 誤實作為只改 Ebiten camera，也不可在 cutscene node
邊界清掉 battle 留下的 visible cursor provenance。

這項連續性是 `0x24B4D` 的前置資料邊界：後者的 terrain staging
讀當時 camera，不是 `battle_ch29` 入口 camera。重製端必須保留
pan/focus 後的 typed `NativeMapViewState`，再讓 transition consumer 讀取；
任一六欄缺少或越界時在更改 frame buffer 前失敗即關閉。這是
E1 state-flow 規格，不單獨宣稱原版玩家戰鬥結束時的特定游標座標。

## 正式重製接線狀態（2026-08-21 勘誤）

本檔前段「正式 binding、`0x1DB65` presenter、group9 與
`preparation_ch30` 尚未完成」是研究過程的歷史 gate，現已被取代。
當前正式路徑已按下列順序通過 Docker／Xvfb 決定性回歸：

```text
story_ch29 -> ch28_pre -> battle_ch29
-> postbattle_ch29_persist / ch28_post
-> preparation_ch30 -> save -> load -> preparation_ch30
```

此路徑物化已證實的戰鬥入口 view／HUD，消費
`0x35BBA→0x1DB65` 的13＋6＋6呈現、追加group9、以動態尾slot執行
`0x25535→0x22253`，並播放`0x24B4D`與`0x35E5A`後同步持續隊伍。
這項狀態為`RUNTIME-E1`；未修改DOS一般玩家路徑、同狀態逐幀／聽覺
`PLAYER-E2`、entries `0x44..0x4F`與sample index3的高階語意仍未閉合。

## `0x35bba(20)` 與共用 `0x1db65` raw 邊界（2026-08-09）

合法 IDA Pro 9.4 與 Docker Capstone 以同一固定版 `FD2.EXE` 重新檢查
`0x35bba`、`0x1db65`。`sub_35BBA` 的完整 raw 形狀是：從呼叫者傳入的
起始索引開始，逐筆走到 `[0x53beb]`，對每筆 0x50-byte runtime record
清除 word `[record+0x40]`，然後呼叫共用 `sub_1DB65`。因此
`0x35bba(20)` 可保存為「範圍清除 `record+0x40`」原語；沒有證據可以把
這個欄位命名成 HP、狀態或角色資料。

`sub_1DB65` 的 caller 不只 `0x35bba`，還包括 `0x15447`、`0x15643`、
`0x18fe0`、`0x1a941`、`0x1d497`、`0x21062` 與 `0x3543d`。其 raw body
會掃描每筆 record 的 byte `+0/+1/+5` 與 word `+0x40`，依多個共用
global 計算索引緩衝區位址，並呼叫 `0x129ec`、`0x11eee`、`0x17aa9`、
`0x127e0`、`0x4e85b` 及 `memmove`。這只證實它是共用的 indexed
呈現／更新消費端候選；沒有證據把它命名成 ch29 專用 renderer、AI、HP
重設或 campaign owner。

本節關閉「`0x35bba` 完全未知」的過時斷言，但不關閉
`0x1db65` 的高階欄位語意、indexed frame provenance、一般玩家 E2，亦不
授權 `postbattle_ch29_persist` 接到 preparation、town、shop、整備或
save。原始位址、caller 與所有運算元仍以本檔及固定版雜湊為準。

## map28 runtime topology 稽核與 E1 adapter 邊界（2026-08-21）

固定版 FDFIELD map28 有76筆控制 record、20筆 own deployment position；控制
群組分布為 group1/2/3各3筆、group4/5/6/7各2筆、group8共56筆、group9共1筆、
group255共2筆。`ch28_pre` 的直接指令只明確顯示 LOADCH index28 後以
`0x35822(group8,19,9)` 追加 group8；`ch28_post` 再於 `0x25505` 呼叫
`0x10B4E(9)`，然後以 `[0x53BEB]-1` 呼叫 `0x22253`。共用 `0x1088D`／
`0x10B4E` 證據支持「persistent records 先置於 runtime 起始區，group append
使用目前 count 作新 slot 並遞增」。

這些證據已證實 `0x25535` 的 unit 是**呼叫當下最後一個 materialized slot**，
但尚未證實 groups1..7 在一般玩家第29戰的 writer／時序。若假設20名 party、
groups1..7共17、group8共56、group9共1依序全部 materialize，最後會是 slot93；
這只屬**強推論**，不可寫入 binding 或 runtime 常數。現行 `ch29.json` 把 groups1..9
列為 initial groups，且 legacy Setup 先保留76筆 map rows再 append party，與原版
append topology 不等價；正式接線前必須先修正這個資料邊界並取得相符 writer 證據。

在不依賴固定 slot93的範圍內，重製端已完成兩個窄 adapter：

- `native_unit_present` 只對來源 `0x25535` 接受 dynamic last slot 與
  `(15,10,15,10)`；預先合成11＋6＋18/24＋10個可見邊界，第六張 contract
  呈現後才寫座標，失敗回復 unit／work／VGA。
- `native_palette_pulse` 依 `0x35E5A` 執行0..63、400ms hold、62..0共127次
  immutable-baseline DAC present，拒絕端點漂移。

上述為 `RUNTIME-E1` primitive／caller slice，不是 `postbattle_ch29_persist`
正式 binding。dialog／pan binding、group topology、持續隊伍、`preparation_ch30`
save/load與未修改原版 E2 未完成前，campaign 仍失敗即關閉。
