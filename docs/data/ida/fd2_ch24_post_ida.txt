# FD2 ch24/ch25 post raw handler 證據（IDA／Capstone）

## 輸入與位址基準

- 輸入：`FD2.EXE`，357074 bytes。
- MD5：`b97caf2239a27a896069d03549d96e1e`。
- SHA-256：`222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f`。
- 第一順位工具：合法 IDA Pro 9.4 Docker，保留 IDA 原始函式名與線性位址。
- 交叉驗證：Capstone 5 Docker，`tools/disasm_le.py` 的線性位址。
- 本檔所有語意都是附加註記；原始函式名、位址、運算元與呼叫順序保留。

## 已證實：raw handler table 與函式邊界

資料映像的 handler table 位於線性位址 `0x51de9`，同一批 LE 輸入的檔案偏移
是 `0x51be9`。本版 raw entry bytes 如下：

| table index | file offset | raw bytes | raw little-endian | linear address |
| ---: | ---: | --- | ---: | ---: |
| 23 | `0x51c45` | `1e 4c 01 00` | `0x14c1e` | `0x24c1e` |
| 24 | `0x51c49` | `f2 4d 01 00` | `0x14df2` | `0x24df2` |
| 25 | `0x51c4d` | `80 4e 01 00` | `0x14e80` | `0x24e80` |

IDA Pro 9.4 將 `0x24df2..0x24e80` 識別為 `sub_24DF2`，唯一直接 caller 是
`0x25e23` 的 table consumer（`call funcs_25E23[eax*4]`）。`0x24e80..0x25052`
是相鄰的獨立函式 `sub_24E80`，同樣由 `0x25e23` 間接呼叫。table index 只固定
raw dispatch 與函式邊界，不可直接命名成玩家戰次；玩家第25／26戰的 owner 仍需
以 map、文字、執行期路徑交叉閉合。

## 已證實：`sub_24DF2` 的原始順序

Capstone 與 IDA 指令逐項一致，`0x24df2` 依序執行：

1. `push 0x28` → `call 0x36cd7`。
2. `0x24e1b` 呼叫 `0x15f84`，保留 raw 參數與文字指標 `[0x53a79]`，立即值含
   `6`；現有文字證據將此標為 FDTXT_025 index6。
3. `0x24e27` 呼叫 `0x135dd`，原始 push 順序為 `push 0x10`、`push 4`；依既有
   tile ABI 的附加換算是 PAN raw `(4,16)` → `(96,384)`，不改寫原始參數。
4. `0x24e31` 呼叫 `0x10b4e`，立即值為 `2`；保存為 raw spawn 呼叫
   `0x10b4e(2)`，不把 `2` 猜成角色、隊伍或 JOIN 語意。
5. `0x24e3b` 呼叫 `0x1366a`，立即值為 `0x4b`（十進位75）；現有 acting
   exporter 證據對應 ACTING resource75，解碼為4 beats、slot70、pose2。
6. `0x24e62` 再呼叫 `0x15f84`，文字立即值為 `7`；現有文字證據將此標為
   FDTXT_025 index7。
7. `0x24e6c` 呼叫共享函式 `0x112a5`，立即值為 `0x1a`；`0x112a5` 的 raw
   行為是將 persistent record append 至 `[0x53bf7] + [0x53bfb]*0x50`、寫入
   原始欄位、呼叫 `0x1145a` 後增加 `[0x53bfb]`。`sub_4e4e8(id)` 的 32 列
   固定角色表與 `characters.json`／`native_character_catalog.json` 共同證實
   `0x1a`（十進位 26）是角色索引「聖寇拉斯」。同一個 persistent 建構器在
   其他已閉合 handler 中以 `join` 編輯操作消費；map24 的 authored party 沒有
   26，而 map24 group0 唯一我方 raw unit 正是 26，因此本次操作可提升為
   **強推論：可編輯永久 JOIN 26**，但仍不把「post handler 可直接接到 battle
   State」的 runtime roster 邊界當成已證實。
8. `0x24e74` 呼叫 `0x11506`。
9. `0x24e7b` 將 raw immediate `0x1d`（十進位 29）壓入堆疊後跳到
   `0x237c8`。Capstone 對 `0x23790..0x237d5` 的直接指令顯示：
   `0x237c6` 才是 direct-entry 的 `push 0x0e`，`0x237c8` 本身是
   `call 0x112a5`；因此從 `0x24e7b` 跳入時會跳過固定的 `push 0x0e`，
   `0x112a5` 實際消費呼叫者壓入的 `0x1d`，不是角色14。IDA 偽程式碼的
   `sub_23790()` 只描述從函式起點進入的預設 14，不能覆蓋這個中途跳入的
   堆疊 ABI。ch12 的 `push 3 → jmp 0x237c8` 與 ch14 的同型呼叫是交叉證據。
   固定角色表確認 29 為「亞奇梅吉」；map24 group2 唯一敵方 raw unit 也是
   29，後續 ch26–ch30 authored party 同時列出 26／29。因此本次共享尾段可
   提升為 **強推論：可編輯永久 JOIN 29**，原始位址仍保留為 `0x24e7b→0x237c8`。

以上是 E1 靜態控制流程證據。它支持「raw handler 有兩段對話、PAN、spawn、
ACTING、JOIN 建構器 26／29 與共享尾段」。本檔舊版曾因重製端預載全部70筆
map control再加16名隊員而得到錯誤的86-slot State，並據此阻擋正式接線；
2026-08-13的執行期拓撲勘誤見下方「目前判定」。

## 已證實：`0x10b4e(2)` 的 FDFIELD group materializer 與 map24 列數

本輪以合法 IDA Pro 9.4 追查 `sub_10B4E`（`0x10b4e..0x10c50`）及其唯一
直接 callee `sub_10C50`（`0x10c50..0x11019`）。`sub_10B4E` 先開啟
`FDICON.B24`，以 `sub_111BA` 讀取 `FDFIELD.DAT` 的 current field 資料，從
`[0x53a55]+0x83` 起按 0x1a-byte stride 掃描 `[0x53be3]` 筆列；只有 row
`+0x15 == arg_0` 才在 `0x10bec..0x10bf2` 呼叫 `sub_10C50(row_index,
FDICON_stream)`。`sub_10C50` 依 raw row 與 position record 選擇座標、建立
`[0x53a45] + [0x53beb] * 0x50` runtime record，最後遞增 `[0x53beb]`。因此
這裡的「spawn」是可編輯 FDFIELD group materializer；不是角色身分或 JOIN
語意。兩個函式的原始名稱、位址與運算元均保留，語意仍是附加註記。

固定版原始 `FDFIELD.DAT` 解包 resource 073（map24 control）為 1951 bytes，
MD5 `d64cca11484662bd45ab6c34aeb63ff9`、SHA-256
`433bc1a2146c22598b42a53b1fbd901bce54bc4328147613128f69ad483b177b`；header
後的 70 筆列分布為 group0=46、group1=8、group2=1、group255=15，group2
唯一列索引為 54。可編輯 `remake/assets/maps/map24/map24_units.json` 的
第 54 筆也只有一筆 `group=2`（座標 `(10,24)`、raw key 29），與原始列的
`+0x15=2` 及 position record 相符。這證實候選 binding 的
`runtime_context.spawn_groups["2"] = 1` 是列數投影，不是猜測的角色數；
`0x112a5(0x1a/0x0e)` 的建構器角色索引已分別辨識為聖寇拉斯／珊，但仍不證實
一般玩家戰後 runtime frontier、永久 JOIN 或其他隊伍操作。

## 已證實：相鄰 `sub_24E80` 的邊界，不與 `0x24DF2` 混稱

`0x24e80` 開頭以 `push 0x6c` 呼叫 `0x36cd7`，掃描 runtime index
`0x10..[0x53beb)-1`；若 record byte `+7 == 0x1f`，就寫入 byte `+0 = 0x10`、
`+1 = 0x06`。接著呼叫 `0x233c6` 的 16-slot layout、FDTXT／ACTING 資源，
最後增加 `[0x53c03]` 並跳至 `0x15487`。這是 table index25／相鄰 handler 的
獨立函式，不可將它的 layout 與 `0x24df2` 的 raw caller 混合。

## 目前判定與2026-08-13執行期勘誤

  `postbattle_ch24_persist` 曾因錯誤的70對86拓撲而 blocked，但本段下方的

  ACTING75、event56與campaign graph交叉閉合。
- `0x1a`／`0x1d` 的建構器角色索引與中途跳入的堆疊參數已辨識為 26／29，
  可編輯腳本已保留為`join`26／29。舊70對86衝突已撤回：原版追加式runtime
  是party16＋group0(46)=62，第6回合event56於`0x3549f`追加group1(8)成70；
  post handler的`0x10b4e(2)`再追加唯一group2成71，ACTING75操作slot70。
