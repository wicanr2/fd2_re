# FD2 raw ch29 montage 後續尾端：IDA Pro 9.4／Capstone 證據

## 輸入與工具

- 輸入：`FD2.EXE`，大小 357074 位元組。
- MD5：`b97caf2239a27a896069d03549d96e1e`。
- SHA-256：`222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f`。
- IDA：合法 IDA Pro 9.4，`fd2-ida-authorized-local`，一次性無網路 Docker。
- 交叉驗證：`fd2-cap-local` Docker 內 Capstone 5.0.3。
- 所有 `0x...` 均為 FD2.EXE 線性位址，不是檔案偏移或重製端位址。
- `FDFIELD.DAT`：大小 243169，MD5 `ecdb0436d26adfe5d107f2713fa7e9a2`，
  SHA-256 `b0cf75d94f58603f091c7462c0494f0e83bd6edfb04c1acbf83ed4d938c7a513`。
- `FDICON.B24`：大小 624010，MD5 `46f793540209a063ea73a5373ca14bf4`，
  SHA-256 `7efb4448d05f19c1e17ebd53f3e3afead235f5c008d5167548d834c3686b1e44`。

## 已證實：`0x2c194..0x2c39a` 呼叫順序

`0x2c18f` 由 `0x2bce5` 呼叫 `0x2c405`；`0x2c194` 是該函式在
`0x2c405` 返回後的下一段，不是直接返回 campaign。Capstone 直接指令固定：

```text
0x2c194  push 0xfa00; push 0; push 0xa0000; call 0x375c0
0x2c1a8  push 1; push -1; call 0x25977
0x2c1b4  push 0x32; call 0x17aa9
0x2c1be  push 0x3c; push [esp+0x48]; push 0x1a4d; call 0x111ba
0x2c1d3  push -1; push 0x140; push 0xa0000; ...; call 0x4e63d
0x2c1ec  call 0x1f525
0x2c1f3  push 0; push 0x12; call 0x25977
0x2c1fd  push 0x50; call 0x17aa9
0x2c207  call 0x1f882
0x2c220  push 0x3a; push esi; push 0x1a4d; call 0x111ba
0x2c234  push 0x39; push [esp+0x44]; push 0x1a4d; call 0x111ba
```

以上只提升資源索引、配置／透明解碼與等待呼叫的 raw 契約；`0x25977`、
`0x1f525` 與 `0x4e63d` 的完整語意仍不可由這段單獨命名。

## 已證實：20-entry raw table loop

固定版 FD2.EXE 的**線性位址** `0x525dc..0x52617`（LE object 2，對應檔案偏移
`0x523dc..0x52417`）的 60 bytes 被分成三組各 20 bytes：

```text
linear 0x525dc..0x525ef / file 0x523dc..0x523ef  record0_byte_7
linear 0x525f0..0x52603 / file 0x523f0..0x52403  record1_byte_7
linear 0x52604..0x52617 / file 0x52404..0x52417  global_540ff

record0_byte_7 = 33 6e 13 69 36 75 1e 7b 27 7f 40 51 34 7d 1a 73 29 5b 1f 7e
record1_byte_7 = 67 14 53 1c 7c 26 5d 22 70 2c 56 35 50 37 78 24 6a 3c 7a 32
global_540ff   = 04 03 33 0e 19 12 28 35 16 18 1c 11 1e 1f 32 21 22 34 24 2f
```

Capstone 固定迴圈 `0x2c253..0x2c33b`：

```text
0x2c258/0x2c32c  [0x53a45]+6 = (record0_byte_7[i] < 0x4c ? 2 : 0)
0x2c268             [0x53a45]+7 = record0_byte_7[i]
0x2c274/0x2c285  [0x53a45]+0x56 = (record1_byte_7[i] < 0x4c ? 2 : 0)
0x2c299             [0x53a45]+0x57 = record1_byte_7[i]
0x2c2a0  [0x540ff] = byte[stack+i]
0x2c2a6  call 0x28a6c(0,1)
0x2c2bb  call 0x11d40(0,255,0)
0x2c2cc  call 0x17aa9(0x14)
0x2c2d6  call 0x2935b(resource_58,i,0xa0000,0x140,-1)
0x2c2ef  call 0x17aa9(0x4e)
0x2c2f9  call 0x1f882
0x2c302  call 0x375c0(0xa0000,0,0xfa00)
0x2c313  i++ ; i < 0x14
```

`[0x53a45]+0x56/+0x57` 與 runtime stride `0x50` 相減後，正是第 1 筆
record 的 `+6/+7`，不是第 0 筆 record 的高位欄位。兩組 selector byte 都依
各自 `<0x4c ? 2 : 0` **即時計算**對應 record 的 `+6`；那不是第四或第五張
20-byte table。所有 20 筆都會寫入這兩筆 record。各 byte 仍只保留 raw 表名，
不可升格為角色、職業、動畫或結局名稱。
重製端以 `native_2c194_tail.json` 與 `MontageTail.Plan` 保存這個可編輯
schedule；為拒絕舊的轉置欄位合約，該資產 schema 已升為 2。它只產生 raw entry，
不直接寫入 `battle.State` 或呈現畫面。

資源角色勘誤：`0x2c220` 載入的是 FDOTHER #58；其資源表可解出 20 個 frame，
也正是 `0x2c2d6` 傳入 `0x2935b` 的來源。`0x2c234` 載入的是 FDOTHER #57；它剛好
是 768 bytes（256×3），在 `0x2c2b6` 指派到 `[0x53a65]` 後交給 `0x11d40`。先前把
frame call 寫成 `resource_57` 是 stack resource index 的錯置，現已撤回；這項勘誤
不為三組 raw table 或 `0x28a6c` 增加任何角色／演出語意。
FDOTHER #58 的 20 筆 descriptor 幾何也以玩家提供檔案 regression 固定，例如第 0 筆
為 `(15,7,55,98)`、第 19 筆為 `(39,71,237,28)`；這只證實 frame-table layout，
不替各 frame 命名或推斷其畫面角色。

## 已證實：`0x1088d(0x1e)` 的 post-loader record 基線

正確 caller 是 `0x2c435 push 0x1e`、`0x2c437 call 0x1088d`；較早把呼叫點寫成
`0x2c469` 是時序誤植。固定 selector 使用 FDFIELD #90/#91/#92：#90 是 35×45
地圖；#91 header 為 `(30,31,1)`，唯一 unit row 的 group byte 是 255；#92 有
32 筆位置，第一筆屬 control row，後 31 筆才是 deployment slots。

`0x1088d` 會配置 31×`0x50` runtime records。對每筆有效 persistent record，
`0x10a77` 先複製完整 `0x50` bytes，再由 deployment position 寫 `+0/+1`、
`0x11019(record[+7])` 寫 selector cache slot 到 `+2`、清 `+3/+4`、寫 `+6=2`、
`+0x31=0xff`、清 `+0x22..+0x27`，最後呼叫 `0x1b750`；其餘 deployment
records 清零後只寫 `+5=1`。尾端 `0x10b4e(0)` 只追加 group 0，而 #91 唯一 row
是 group 255，因此不增加第 32 筆 record。

重製端 `MontageTailLoaderBaseline` 以真實 FDFIELD／FDICON／item table 回歸這個
31-record 形狀，並只暴露 value copy。這是 **post-`0x1088d` baseline**，不是
`0x2c2a6` renderer admission：中間的 `0x2c548` 可觀察或改動同一 runtime image，
目前沒有一般玩家 trace 證明呼叫時完整 record 內容。

## 已證實：`[0x540ff]!=0` 仍有可見消費鏈

IDA 9.4 資料流與 Capstone 直接指令交叉確認：`0x28c15` 起依 `[0x540ff]`
選 TAI／BG（特定 raw `record[+7]` 組合則選 TAI #3），並載入
`3*record1[+7]`、`3*record0[+7]`、`3*record0[+7]+1` 的 FIGANI 資源。
接著呼叫 `0x29164` 與 `0x2939d`；`0x29164` 的 `+6==0`／非零兩支都執行
九階段合成、`0x2935b`、VGA copy 與 `0x11d40`。

`0x2939d` 只在 `[0x540ff]==0` 呼叫 `0x29f72` 一般戰鬥結果解析器；非零時把
相關結果欄位歸零，但仍執行 frame loop、`0x2935b`、`0x11eb0`、等待與
`0x29c90`／`0x29ded`。所以「非零分支沒有畫面」是錯誤斷言；正確限制是：
原版視覺輸出鏈已達 E0，但精確呼叫時輸入、20 段可見結果、重製轉接器與 E2
尚未閉合，正式路徑仍須失敗即關閉。

## 已證實：尾端收尾

`0x2c33b` 後恢復 `[0x53a65]`、釋放 #58，等待 `0x17aa9(0x32)`，載入
FDOTHER #59、以 `0x4e63d` 解碼到 VGA、呼叫 `0x1f525`，釋放資源後從
`0x2c39a` 返回。這只是 presentation／資源生命週期，尚未證明 campaign
node、town、shop、整備、save 或結局 owner。

## 推論等級與限制

- 已證實：四個 FDOTHER resource index、三組 20-byte raw table、兩個
  `0x50`-stride runtime records 的 `+6/+7` 寫入、20 次 loop、
  `0x28a6c`／`0x11d40`／`0x2935b`／`0x1f882`／`0x375c0` 的直接呼叫形狀。
- 已證實：上述 table 的定位是 IDA／Capstone LE 線性位址；它們位於 object 2，
  所以檔案偏移是線性位址減 `0x200`。不可把兩種基準混作同一個 `0x...`。
- 未知：各 raw table 欄位的遊戲名稱、`0x25977`／`0x1f525` 的完整語意、
  `0x2c2a6` 呼叫當下完整 records/globals、20 段重製轉接器，以及這段與
  終局／戰役／城鎮的 handoff。

因此 `MontageTail` 目前是可編輯、可驗證、失敗即關閉的 raw schedule，
不是 campaign binding，也不解除 `postbattle_ch29_persist`。
