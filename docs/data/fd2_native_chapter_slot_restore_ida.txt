`0x25EBB` 的章節槽載入分支
--------------------------

IDA 將 `0x25EBB..0x26152` 定為同一函式；`0x26019` 呼叫四槽 selector
`0x30550`。確認後的直接指令如下：

1. `0x2602C..0x26048` 以 `[0x53C57]` 計算
   `save+0x312B+slot*0xA28`。
2. `0x2604A..0x26056` 從 record 起點複製固定 `0xA00` bytes 到
   `[0x53BF7]`。這是 32 筆、每筆 `0x50` bytes 的 persistent roster。
3. `0x2605E` 將來源移至 record `+0xA00`，接著依序載入：
   - `0x26064..0x26067`：metadata `+0` → `[0x53C03]`
   - `0x2606C..0x26070`：metadata `+1` → `[0x53BFB]`
   - `0x26075..0x26078`：metadata `+2..+5` → `[0x53BF3]`
   - `0x2607D..0x26098`：metadata `+6/+7/+8/+9` →
     `[0x51AAB]/[0x53AF9]/[0x51E61]/[0x51E62]`
4. `0x2609D..0x260A9` 只以 chapter raw `0xFF` 將 selector 結果改為
   未確認；`0x260AB` 關閉畫面後，結果為零便回到 `0x26016` 重選。
5. 非空且 selector 回傳 1 時，`0x260DE` 先清 raw gate，
   `0x260E5` 呼叫 `0x2CAD7`。只有 gate 回傳 0，才在
   `0x260F0..0x260F5` 依 `[0x53C03]` 呼叫章節 pre-handler 跳表；
   隨後 `0x260FC..0x2610A` 依章節表呼叫 `0x25977`。

`0x30012` 的章節槽寫入端與合法恢復落點
-----------------------------------------

IDA 將 `0x30012..0x301F4` 定為同一函式；只有兩個直接呼叫者：

- `0x2CCB6`：`0x2CAD7` 的直接整備分支；
- `0x2FD93`：酒店／休息流程 `0x2FC85`。

writer 在 `0x300C8..0x300D4` 先將 `[0x53BF7]` 的固定 `0xA00`
bytes roster 寫入選定 record，再於 `0x300E2..0x30116` 依序寫：

- metadata `+0` ← `[0x53C03]`
- metadata `+1` ← `[0x53BFB]`
- metadata `+2..+5` ← `[0x53BF3]`
- metadata `+6` ← `[0x51AAB]`
- metadata `+7` ← `[0x53AF9]`
- metadata `+8` ← `[0x51E61]`
- metadata `+9` ← `[0x51E62]`

`0x3012D..0x30158` 重算 checksum、套用 rolling XOR 後寫回完整
`0x59CB` bytes。writer、reader 與 `0x30437` renderer 都不生產或消費
metadata `+10..+39`；這個結論只限上述三條已查路徑，不外推為全程未使用。

兩個 writer caller 都位於戰間流程，而且 LOAD reader 載入後重新呼叫
`0x2CAD7`。因此合法恢復點是 gate table 決定的城鎮／整備入口，而不是重播
上一戰的 postbattle handler。`[0x53C03]` 是 zero-based raw chapter index。
較早曾把畫面章數與重製節點尾碼一概寫成 `raw+1`；此概括已由下方 raw `0x1c`
有效槽實驗訂正。原始 `0x526B9` 30-byte table只有
raw index `22..24`、`27..29` 為1：

- gate 0：預設 `town_ch(raw+1)`；
- gate 1：預設 `preparation_ch(raw+1)`；
- raw `0x1c` 的已證實有效落點例外見下方勘誤。

這也表示 ch21 的物品合成與 ch27 的物品 gate 已在存檔前執行；LOAD 不得
回到 `inventory_recipe_ch21_sky_key` 或
`inventory_gate_ch27_sky_key`。raw chapter 0 在現行戰役圖沒有
`town_ch01`，重製端會失敗即關閉，不自行創造第一章可存檔點。

範圍限制
--------

- 這條四槽章節載入路徑不呼叫 `0x10010`。`0x26130→0x10010` 屬標題
  選單第三分支的「目前戰鬥續戰」入口，兩者不可合併。
- 原版在本段固定複製完整 roster，沒有看到對 metadata roster count
  `+1` 的容量檢查。重製端拒絕 count > 32 是安全邊界，不宣稱為原版
  行為。
- 本段證實複製順序、raw globals、writer caller 與戰間分派；
  `PersistentRecord→battle.Unit` 只投影已有 writer／consumer 的欄位，
  不填 portrait、sprite、座標、spells 或 attack range。
- 使用者目前未修改的四槽皆為空槽；因此 production restore 目前只有合成
  checksum-valid fixture 的決定性 E1 測試，沒有一般玩家有效存檔的 E2
  成功還原實驗。

重製對應
--------

- `remake/internal/fdsave.InspectChapterSlot` 保存相同的固定邊界：
  32×`0x50` 完整 raw record、全部 `0x28` metadata，以及只含已證實
  `chapter/roster_count/currency/HUDGateA/Raw53AF9/Raw51E61/Raw51E62`
  的 `VerifiedMetadata`。
- 空槽與 count > 32 採失敗即關閉；metadata `+10..+39` 與未投影 roster
  bytes 原樣保留，不猜成戰役旗標、角色或戰鬥數值。
- 設定 `FD2_NATIVE_SAVE` 時，production title compositor 會以
  `fdsave.Decode→ReadVerifiedMetadata` 讀取四槽 chapter／empty 狀態；
  checksum 錯誤會拒絕整份資料。空槽確認留在 selector，不再錯誤退出標題。
- `native_intermission_gate.json` 保存版本雜湊與 `0x526B9` 30-byte 表。
  `BuildNativeChapterSlotRestorePlan` 會先驗證 chapter、節點型別、完整
  persistent party 與重複 identity，再由 production title 一次套用
  campaign cursor、gold、party 與 raw metadata 保存值；任何錯誤都留在
  selector，不轉呼 JSON loader，也不部分改寫現有遊戲狀態。

2026-08-26 有效晚期槽勘誤
---------------------------

較早把所有有效落點直接概括成 `raw+1`，只證實了 `0x526B9` gate 選擇城鎮或
整備的窄作用，沒有證實 `0x2CAD7` 及後續 pre-handler 對每個 raw chapter 的最終
玩家可見節點。固定雜湊 `fd2last.sav` 的 slot 0 保存 raw chapter `0x1c`；未修改
固定版 `FD2.EXE` 由普通標題 LOAD、save-NO 與19次 Return 連續抵達最終戰。重製
正式 selector 對同檔的聚焦測試則證明舊映射會停在 `preparation_ch29`，直接反證
這個 raw 值的有效落點可由 `raw+1` 單獨推出。

此勘誤不替間接控制流猜測內部 writer，也不改寫原始 30-byte table。重製資料層
必須保留該表，另以來源綁定的 effective-route override 把 raw `0x1c` 導向
`preparation_ch30`；證據來源為
`docs/data/ui-traces/native-load-ch29-slot-to-ch30-original-candidate.json`，等級限於
「已證實此固定輸入的玩家可見落點」。其他 raw chapter 仍沿用既有規則，只有新的
直接指令或同狀態執行反證才可增加 override。
