# 108 — 地形移動成本表與移動確認的游標（2026-09-11）

本輪的目標是讓重製端自己把第一關從頭打到勝利。過程中連續撞到五個問題，其中
兩個是原版語意被讀錯，錯得夠久也夠隱蔽——它們互相抵消，所以既有回歸全綠。

原版證據一律來自固定版本 `FD2.EXE`：357074 位元組，
MD5 `b97caf2239a27a896069d03549d96e1e`，
SHA-256 `222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f`。
反組譯以 capstone（`tools/disasm_le.py`，`fd2-cap-local`）取得，位址為 LE
linear。

## 1. 移動成本表整份早一個位元組

`0x4E555` 是成本列取得函式，只有三行：

```text
0x04E558  mov eax, [ebp+8]        ; selector
0x04E55B  mov edx, 0x14           ; 每列 20 byte
0x04E560  mul edx
0x04E562  lea edx, [0x61646]      ; 表基底
0x04E568  add eax, edx
```

進格判定在 `0x4E330`（與 `0x4E16E` 同一段邏輯的兩個入口）：

```text
0x04E332  mov ax, word ptr [ebx-3] ; 該格的 tile
0x04E336  and ah, 3                ; tile &= 0x3FF
0x04E339  shl ax, 2                ; ×4
0x04E33D  add eax, [0x60060]       ; + 地形控制表基底
0x04E343  inc eax                  ; +1 → 控制記錄的 byte1 = 地形碼
0x04E344  mov ch, [eax]
0x04E34A  sub cl, [esi+eax]        ; 剩餘預算 -= 成本列[地形碼]
0x04E34D  jb  0x4E1A4              ; 借位 → 進不去
```

索引是**地形碼本身**，沒有偏移。所以成本列的第 n 個 byte 就是地形碼 n 的成本。

問題出在匯出：`tools/dump_exe_tables.py` 把 linear `0x61646` 對到檔案
`0x55445`。實際的對位是 `0x55446`——`18 01 12 00 17` 這串在檔案裡只出現一次，
位於 `0x55440`，而反組譯把它放在 linear `0x61640`。整份表因此早一個位元組。

錯位前後的語意（地形碼語意出自 `references/text/modify2.md` 的靜態定義，
扣減值出自 `references/text/notes.md` 的玩家實測，兩份互相獨立）：

| 地形碼 | 語意 | 錯位時的成本 | 修正後（步行／騎兵／飛行） |
|---|---|---|---|
| 0 | 正常 | 1 | 1 ／ 1 ／ 1 |
| 1 | 不可移動 | **1** | **20** ／ 20 ／ 1 |
| 2 | 森林·僅騎兵減速 | **20** | **1** ／ **2** ／ 1 |
| 3 | 森林·全體減速 | 1 | 2 ／ 3 ／ 1 |
| 4 | 沼澤·全體減速 | 2 | 2 ／ 3 ／ 1 |
| 5 | 不可移動 | 2 | 20 ／ 20 ／ **20** |

修正後每一格都對得上：步行在森林不減速、騎兵 −2、沼澤步行 −2 騎兵 −3、飛行
一律 −1 且只有地形碼 5 擋得住它。錯位時則是**海與房舍可以走進去、森林變成
牆**——第一關地圖 24×24 裡有 85 格森林、128 格海與建築，整張圖的通行性等於
反過來。

實際後果在第一關看得最清楚：援軍 group 4 由 ACT 腳本走位到 (15,21)，那格是
森林、四周也是森林。錯位時盜賊（職業 7）進得去卻出不來，我方也打不到它，
敵方全滅永遠達不成。

修正：`tools/dump_exe_tables.py` 的 `file_base` 改成 `0x55446`，重新產生
`remake/assets/data/native_movement_cost_rows.json`。
`TestLoadNativeMovementCostRowsFixture` 改成以**語意**當錨點（不可移動=20、
森林步行=1 騎兵=2、沼澤=2/3、飛行列碼 0..4 皆 1 碼 5 為 20），錯位會直接掉出來。

## 2. 移動確認時游標回到單位，走的是 0x12CEA 不是 0x149F8

玩家選好落腳格按 Enter 之後，游標會回到單位所在格。早先把這條路標成
`0x149F8` 並實作成「只寫絕對游標的瞬跳」。**那個歸因是錯的。**

`0x149F8..0x14B16` 是沿直線收集單位的 helper：`0x14A5A` 先把目前游標存到堆疊、
`0x14A6F/0x14A78` 設成起點、迴圈逐格 `0x14A90/0x14A9A` 前進並呼叫 `0x12C0D`
收集單位索引，`0x14AFE/0x14B01/0x14B0A` 在結尾**把游標還原**。淨效果是零。

真正的路徑在 `0x18960`：確認之後先把 `[0x53AB1]`／`[0x53AB5]` 存進堆疊，
`0x18A26`（目標無效時是 `0x189AA`）以那個值呼叫 `0x12CEA`。`0x12CEA` 把游標
**先 X 後 Y 逐格**移到目標，每一格都呼叫對應的鍵盤游標處理器：

```text
0x012D09  cmp esi, [0x53AB1]   ; X 到位了嗎
0x012D13  call 0x11C59         ; 左
0x012D1A  call 0x11BFA         ; 右
0x012D42  cmp edi, [0x53AB5]   ; Y 到位了嗎
0x012D4C  call 0x11B48         ; 上
0x012D53  call 0x11B9B         ; 下
```

`0x12D7B` 是同一條路的包裝：讀單位記錄的 x/y 再呼叫 `0x12CEA`。

走鍵盤處理器的後果是**可見游標與鏡頭跟著一起動**。原版三組視圖全域的每個執行期
寫入端都成對搬動：鍵盤與走行步進是「游標±1，可見±1 或鏡頭±1」，劇情 pan
`0x135DD` 是「游標與鏡頭同±1」。因此 `visible == cursor − camera` 在整條互動路上
都成立。

收據 [fd2-move-confirm-cursor-20260909.json](../data/ui-traces/fd2-move-confirm-cursor-20260909.json)
的 cp0071 量到 cursor (8,16)、camera (1,13)、visible (7,2)，看起來差一格——那是
**取樣落在走行步進中途**：`0x13185` 在函式開頭扣可見游標（`0x13205`）、在結尾
才扣游標（`0x1330A`），中間隔著六張動畫幀。把這一格算進去，確認之後的狀態是
cursor (8,16)、visible (7,3)，差值仍是零。

實作成瞬跳的代價是偏差**逐次累積**：每移動一個單位就多累積一次移動量。第一關
跑到第四回合時可見游標已經漂到 (−3,−9)，鍵盤處理器的安全帶判斷（`可見 > 5
才捲鏡頭`）跟著失準，鏡頭再也追不上游標，戰場事件的 pan 最後把絕對游標推出
地圖，整場停在失敗即關閉。

修正：`battle.FocusNativeMapCursor` 逐格走 `MoveNativeMapCursor`（同一套安全帶
規則），移動確認與截圖游標定位共用它。原版每格會重繪一次（`0x11CAC(0)`），
重製端把整段迴圈在同一幀走完——狀態相同，少的是中間那幾張畫面。

絕對游標的場內檢查留著，但理由改寫成**重製端的自我檢查**：原版沒有任何寫入端
夾它（`0x11B52`／`0x11BA5` 的比較在處理器裡而且比的是相等，pan 整段不檢查），
它之所以永遠在場內，是因為寫入端成對搬動、鏡頭被夾在 0..W−13／0..H−8、可見
游標被安全帶留在視窗內。出界就代表某條路徑打破了那個配對。

## 3. 另外三個修正

| 題目 | 原版 | 錯在哪 |
|---|---|---|
| mode 6 移位的地形判準 | `0x11702` 取 `costRow[地形碼]`，`0x11706 cmp eax,0x14` 相等就 `je 0x117A9` 回輸入迴圈 | 重製端寫成「等於 20 才允許」，極性相反。它與第 1 節的錯位在森林格上互相抵消，所以測不出來 |
| AI 的地形特殊判定 | `0x1F183` 在 `+7 == 0x1C` 時 `je 0x1F1C9 → xor eax,eax` **回 0** | `nativeAIIsTerrainSpecialRecord` 把 `+7 == 0x1C` 算成 true，那些單位在 AI 回合會拿到「每種地形都只要 1」的列 |
| 敵方全滅判定 | 記錄 `+5` bit0 = 這一列不在場上（占位格網 `0x145CD`、AI 目標掃描 `0x12C60` 同一判準） | `PendingCount` 把帶 bit0 的列算成「還沒登場的援軍」。第一關 group1+group2 共八列，其中一列帶 bit0（原版戰前資訊顯示 ENEMY·07），敵方全滅之後永遠等不到勝利 |

可見游標為負時的收框也一併修掉：`fdother.RawCell.BlitAtClipped` 在整格落在畫面
外時原本回錯誤，改成 no-op。劇情對白收框的滑動終點就是可見游標，而可見游標
可以是負的（收據見 doc104），那一幀原版也只是什麼都沒畫。

## 4. 第一關完整通關

`remake/cmd/fd2/native_chapter_one_play_test.go` 的
`TestPlayChapterOneToVictory` 讓重製端自己打完第一關：10 回合、我方 2 人存活、
`result == "win"`。中途的加入事件（哈諾／哈瓦特）、兩波敵方援軍（含進場演出與
ACT 走位）、海防隊友軍、寶物提示與戰場事件對白都走過。

**證據等級 `RUNTIME-E1`。** 它驅動的是重製端自己的戰鬥狀態機：選格靠 `g.reach`
算、指令環直接設 `ringSel`、離屏沒有 Draw 所以演出工作的「已呈現」由測試承認
（`fastForwardShotCampaign` 走的是同一種承認方式）。這不是一般玩家鍵盤路徑，
不得冒稱 `PLAYER-E2`；它證明的是「一整關的狀態機自己跑得完，而且每個事件節點
都收得掉」。

戰術是測試自己的啟發式（估計傷害、威脅、原地待機回復），不是原版規則，換一個
種子會走不同的局；`FD2_SEED` 固定成 `20260911` 讓這一條可重現。
