# 105 — 回合橫幅的節奏、暗化與畫面凍結（2026-09-10）

[101](101-phase-banner-20260909.md) 量出橫幅是 33 步對稱馬賽克，但把「馬賽克與
文字的繪製位址」「每步的停留時間」「橫幅開始時左下 HUD 面板在不在」三項留在
未涵蓋。本輪把整條呈現鏈解出來，三項一起關閉。

## 呈現鏈

`RE-CLOSED`。整段由 phase 主控 `sub_1A30B` 起頭，兩處各一次：

| 位址 | 呼叫 | 意義 |
|---|---|---|
| `0x1A525`／`0x1A527` | `sub_1F1CC(0x52)` | 敵方回合橫幅進場 |
| `0x1A52F` | `delay(0x14)` | 中段停留 20 毫秒 |
| `0x1A539`／`0x1A53B` | `sub_1F30A(0x52)` | 敵方回合橫幅退場 |
| `0x1A5CF`／`0x1A5D1` | `sub_1F1CC(0x50)` | 玩家回合橫幅進場，在 `inc [0x53BEF]`（回合數 +1）之後 |
| `0x1A5D9` | `delay(0x96)` | 中段停留 150 毫秒 |
| `0x1A5E6`／`0x1A5E8` | `sub_1F30A(0x50)` | 玩家回合橫幅退場 |

`sub_1F1CC`（進場）：

1. `malloc(0xFA00)`，`memcpy(work, 0xA0000, 0xFA00)` — **保存整幀螢幕 64000 位元組**。
2. `sub_1F42D` 七次（參數 100／75／50／25／0／1／0）— 字樣滑入，每步等一個 BIOS tick。
3. `memcpy([0x53A49]+0x8088, work, 0xFA00)` — 把快照當成之後每一步的來源。
4. 主迴圈 16 次，`ebp` ＝ 1..16、`edi` ＝ 0..15：
   - `sub_4E809(ebp, work, source)` — 馬賽克，方塊邊長 `ebp`
   - `sub_15F0E` 兩次 — 字樣兩塊畫在 (89,86) 與 (169,86)
   - `sub_11D40(0x10, 0xFF, edi)` — DAC 暗化
   - `memcpy(0xA0000, work, 0xFA00)` — **整幀寫回螢幕**
   - `sub_17AA9(1)` — 等一個 BIOS tick
5. `free`、`sub_4E031`。

`sub_1F30A`（退場）：`ebp` 由 `0x11`（17）遞減、`edi` 由 `0x10`（16）遞減到 0，
共 **17 步**，每步結構與進場相同；結束後 `sub_11EEE` 重繪地形、`sub_127A9` 前景，
再跑五次 `sub_1F42D`（0／25／50／75／100）讓字樣滑出。

16 ＋ 17 ＝ 33，正是既有收據量到的步數；邊長 1..16 接 17..1 也正是量到的
`1 + min(f, 32 − f)` 曲線。

### 執行期把這個結構逐幀對上了

`RUNTIME-E1`。以 `sub_1F1CC`／`sub_1F30A`／`sub_1F42D`／`sub_4E809`／`sub_17AA9`
等十六個位址重跑 `-eip-watch`（收據
[fd2-phase-banner-runtime-20260910.json](../data/ui-traces/fd2-phase-banner-runtime-20260910.json)），
靜態讀出來的順序在執行期完全成立：

| 幀 | 觀測到的差值 | 對應 |
|---|---|---|
| idx 97 | `1F1CC` +1、`1F42D` +1 | 進場開始，第一次字樣滑入 |
| idx 98..103 | 每幀 `1F42D` +1、`15F0E` +2、`11EB0` +1、`17AA9` +1 | 其餘六次字樣滑入，合計七次 |
| idx 104..118 | 每幀 `4E809` +1、`11D40` +1、`15F0E` +2、`373C4` +1 | 馬賽克進場 16 步（idx 105 因取樣合併記到 +2） |
| idx 119 | `375B2` +1、`1F30A` +1 | 中段 `delay(20ms)`，緊接退場開始 |
| idx 120..135 | 同進場的每步組合 | 馬賽克退場，合計 17 步 |
| idx 136 | `4E809` 0 | 退場結束 |

七次 `sub_1F42D` 與程式碼裡的七次呼叫（參數 100／75／50／25／0／1／0）數量相符，
`sub_1F30A` 出現在 `delay` 的同一幀也與 `0x1A52F`→`0x1A53B` 的順序相符。這同時
解掉了先前「馬賽克開始前那七幀是什麼」的疑問：它們就是字樣滑入。

### 馬賽克核心 `sub_4E809`

`RE-CLOSED`。參數為（邊長, 目的, 來源），本體只有 82 位元組：

```
esi/edi += 0x504          ; 來源與目的都跳到 (4,4)
ah = 0xC0                 ; 192 列
cx = 0x138                ; 312 欄
al = [esi]; stosb         ; 每個輸出像素取目前來源像素
dec dl; jne; mov dl,bl; add esi,ebx   ; 每輸出 bl 個像素，來源才前進 bl
add edi,8                 ; 320 − 312
dec dh; jne; mov dh,bl; add esi,ebp   ; 每 bl 列，來源才換列（ebp = 320 × bl）
```

窗格原點 (4,4)、範圍 312×192、方塊左上角取樣 — 三項都是 2026-09-09 由畫面
量出來的規則，這裡由原始指令證實。

### 節奏：每步一個 BIOS tick

`RE-CLOSED`（指令）／強推論（換算成毫秒）。`sub_17AA9(n)` 的本體是：

```
[0x53A2C] = *(word*)0x46C          ; BIOS tick 計數
loop: eax = *(word*)0x46C − [0x53A2C]
      if (eax < 0) eax += 0x10000  ; 跨 16 位元回繞
      if (eax < n) goto loop
```

橫幅每一步、以及字樣滑入滑出的每一步，結尾都是 `sub_17AA9(1)`。BIOS tick 是
18.2065 Hz，一個 tick ＝ **54.925 毫秒**，所以整段 33 步的原版設計長度是
33 × 54.925 ms ＋ 中段停留 ≈ **1.83 秒**（敵方）／ **1.96 秒**（玩家）。

這個節奏不依賴 CPU 速度，前提是「畫一步的時間小於一個 tick」。

一個 tick 在 dosgolem 上是 **54,926 道指令**。FD2 走的是 LE（DOS/4GW 保護模式）
那條路，它的 BIOS 時鐘由 `InstallLEBIOSClock` 掛在 `CPU.StepHook`，**每道指令
推進一次，一次代表一微秒**；分頻 65536 時累積 `65536 × 264 × 10⁶ ÷ 315×10⁶`
＝ 54,925.7 次才讓 `0000:046C` 加一。dosgolem 的
`TestBIOSClockPeriodMaskAndRollover` 直接釘住這個數字：advance 54,925 次仍是
0，第 54,926 次才進位。54,926 指令 × 1 微秒 ＝ 54.93 毫秒，與 18.2065 Hz 相符。

（`Machine.IRQ0Every`／`CycleClock`／`DefaultCPUHz` 是 real-mode 那條路的時鐘，
與 LE 這條路是兩套，不要互相套用。）

有了這個數字，收據上的步距就解釋得通，而且**與原版契約一致**：

| 段落 | 每步步距 | 換算 | 為什麼 |
|---|---|---|---|
| 字樣滑入 `sub_1F42D` | 約 30,000 指令 | 0.55 tick | 工作量小，步距幾乎全是等待。`sub_17AA9` 每次呼叫都把 base 重設成當下的 `0x46C`，所以是「從現在等到下一次進位」，平均半個 tick ＝ 27,463 指令 |
| 馬賽克 `sub_4E809` | 約 356,000 指令 | 6.5 tick | 畫一步就花掉六個多 tick，等待只補到下一個邊界 |

所以在 dosgolem 上，馬賽克那 33 步的等待**不生效**（工作量遠超過一個 tick），
收據的步距是模擬器畫一步的工作量；而在當年的目標機上，畫一步遠小於一個 tick，
每步就是紮實的 54.925 毫秒。**節奏寫在 `sub_17AA9` 的參數裡，不在步距裡。**

> 2026-09-10 兩次修訂：本段先曾寫成「虛擬 CPU 是每指令 1 微秒」（正確），
> 下午一度以為那是誤讀 oracle metadata 的 `pit_timing` 字串而撤回（錯誤——
> 當時把 real-mode `Machine` 的 `IRQ0Every`／`CycleClock` 誤套到 FD2 走的
> LE 路徑），本輪以 `le_bios_clock.go` 的 `StepHook` 掛載點與那條測試證實
> 一微秒／指令成立，並補上 54,926 這個確切數字。

一項觀測留著不硬解釋：等待迴圈 `0x17AC4` 在 `-eip-watch` 下每步只記到 64～65
次進入，而平均等待 27,463 指令、迴圈本體七道指令，理應是數千圈。可能是
`-eip-watch` 對緊密迴圈的計數方式，也可能是取指令快路徑。它不影響上面的結論
（步距與 tick 的關係由 tick 的指令數直接對上），但要用輪詢次數推算時間之前得先
弄清楚。

中段停留走 Watcom 的 `delay(ms)`（`0x375B2` → `0x3DCCD`）：把毫秒乘上開機時
校準出來的 `[0x541B0]`，再用那麼多次 `int 21h AH=2Ch` 消耗時間。它同樣是設計
意圖寫死在參數裡：敵方 20 毫秒、玩家 150 毫秒。

### 暗化：`sub_11D40(0x10, 0xFF, level)`

`RE-CLOSED`。迴圈 `ebx` 由 `0x10` 到 `0xFF`，每個索引：

```
outb(0x3C8, ebx)
r = [0x53A65][ebx*3 + 0] − level; if (r < 0) r = 0; outb(0x3C9, r)
g = [0x53A65][ebx*3 + 1] − level; if (g < 0) g = 0; outb(0x3C9, g)
b = [0x53A65][ebx*3 + 2] − level; if (b < 0) b = 0; outb(0x3C9, b)
```

`level` 就是迴圈變數 `edi`：進場 0..15，退場 16..0，也就是 **`level ＝ 方塊邊長 − 1`**。
索引 `0x00..0x0F` 不動，橫幅字樣因此不隨地圖變暗。執行期收據每步固定 720 個
DAC 位元組寫入（240 色 × 3），與 `0xFF − 0x10 + 1 ＝ 240` 相符。

2026-09-09 的「整段沒有暗化」只在索引層成立：索引畫面確實逐方塊等於原始幀，
但顯示顏色每步都在變。

### 畫面凍結與左下 HUD 面板

`RE-CLOSED`（機制）／`RUNTIME-E1`（敵方回合實測）。橫幅呈現的是
`sub_1F1CC` 進場時 `memcpy(0xA0000)` 的那一張螢幕，整段不重繪：收據裡
`0x11CAC`（一般重繪）與 `0x11EB0`（窗格 blit）在 33 步期間的差值都是 0，畫面
變化全部來自每步的整幀 `memcpy` 寫回。

因此「橫幅期間 HUD 在不在」不是橫幅自己決定的，而是**進入那一刻螢幕上有什麼**。
實測敵方回合：橫幅第一步（邊長 1，等同原畫面）左下沒有 HUD 面板，游標白框仍在。
`0x1ACF3`／`0x1AD72` 在進入橫幅前的最後一次重繪確實執行過（收據 idx 97），這與
面板不在畫面上並不衝突 — 那一次重繪畫的是不含面板的地圖。

## 重製端的差異與接線

依上述契約，重製端原有三處與原版不同，本輪已修正（見
[`remake/internal/indexedmap/mosaic.go`](../../remake/internal/indexedmap/mosaic.go)
與 `remake/cmd/fd2/main.go` 的 `phaseBanner*`）：

| 項目 | 原版契約 | 先前重製端 | 現在 |
|---|---|---|---|
| 每步停留 | 一個 BIOS tick ＝ 54.925 ms | 自訂 3 幀 ＝ 50 ms | 依 54.925 ms 換算 60 Hz 幀 |
| 中段停留 | 敵方 20 ms、玩家 150 ms | 沒有 | 依 phase 分開 |
| 畫面來源 | 進場時的整幀快照，整段不重繪 | 每幀重新組出來的當前畫面 | 進場時凍結一份 |
| 暗化 | DAC 索引 0x10..0xFF 各減 `邊長 − 1` | 完全不暗化 | 依同一規則 |

## 這一輪用到的兩支工具

兩支都收進版控，下一段動畫節奏的工作可以直接用：

- [`tools/scan_vga_writes.py`](../../tools/scan_vga_writes.py)：掃出所有指向
  VGA 線性位址的立即數。`-eip-watch` 要候選位址，候選要有來源；原版的繪圖呼叫
  幾乎都把目的地當立即數傳進去（地圖窗格就是 `0xA0504`），掃一次就把候選收斂
  到幾十個函式。它掃不到「從全域取得 VGA 基底」的寫入端，那類要另外追指標。
- [`tools/scan_delay_calls.py`](../../tools/scan_delay_calls.py)：列出全部 185
  個 `delay(ms)` 呼叫點與毫秒參數，輸出見
  [fd2_delay_call_sites.txt](../data/fd2_delay_call_sites.txt)。毫秒數寫死在呼叫
  點，是原版的設計意圖，比從模擬器量到的指令數可靠。

方法上值得記住的一條：**節奏要去程式碼裡找等待機制，不要從量到的步距反推**。
橫幅的步距在 dosgolem 上是 356,000 指令，直接換算得不到 54.925 毫秒；但
`sub_17AA9(1)` 一看就知道是一個 BIOS tick。**兩邊的模擬器常數也一樣要讀程式碼**
——這一輪先用輪詢次數反推 tick，繞了兩圈都對不上，最後是 `le_bios_clock.go` 的
掛載點與那條測試給出 54,926 這個確切數字，觀測才一次全部對上。

## 尚未涵蓋

- 玩家回合橫幅（資源 id `0x50`、中段 150 毫秒）只有靜態指令證據，沒有取到同一輪
  的執行期收據。
- 字樣資源 `[0x53A81]` 的 id `0x50`／`0x52` 尚未擷取成資產，字模未比對；重製端
  仍用自己的字型畫 `PLAYER PHASE`／`ENEMY PHASE`。
- `sub_1F42D` 的字樣滑入（7 步）與滑出（5 步）尚未接進重製端。它同樣每步一個
  BIOS tick，位置是 x ＝ `0x55 − 參數`、y ＝ `0x52`，兩塊分別在 (89,86) 與 (169,86)。
- 每步實機毫秒未在真機驗證；「畫一步小於一個 tick」在當年目標機上成立與否，
  只有指令數的間接支持。
- `sub_15F0E`／`sub_15E71`（畫上去並保存背景／還原背景）的資源格式沒有在本輪
  展開。
